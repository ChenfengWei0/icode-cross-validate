# iCode 交叉验证插件：实现细则

本插件为 [openJiuwen/iCode](https://gitcode.com/openJiuwen/iCode) 实现 `交叉验证与组合验证.md`（draft v2，下称"文档"）第 2、3 章的**交叉验证**。

文档规定了做什么，很多地方没有规定怎么做。本文把这些地方逐条定下来，作为实现和核验的依据。

- 每条细则有编号（`细则 N.M`），`STANDARDS.md` 和 checker 按编号引用。
- 细则只补充文档。确有偏离的地方，集中列在第 17 节，逐条说明理由。
- 文档正文和它的例子不一致时，以正文为准，差异同样列在第 17 节。

本文经过一次独立审查，审查意见已经并入（见第 17、18 节）。

---

## 1 范围

细则 1.1　只实现第 3 章"交叉验证的落地"，第 2 章是它的依据。第 4 章组合验证（依赖—保证、前提推断）不实现，也不预留接口。

细则 1.2　交叉验证是收尾检查，只产出可信度报告（概率凭证），不阻止、不打回、不要求主 agent 修改代码。报告不交给主 agent（细则 16.6）。

细则 1.3　文档说"需求在过程中的累加和纠正，由别的机制处理"。本插件把这个机制做成交叉验证上游的独立部分，即第 15、16 节的**需求积累与触发**。交叉验证本身（第 4 至 14 节）只把整理出的 R 当作最终需求。

细则 1.4　不限定被检查代码的语言。所有检查都是"在工作区里运行一条命令"（第 11 节）。

## 2 在 iCode 中的形态

iCode 的扩展点有：工作流、agent 配置、hooks、skills、MCP、外部 ACP agent。iCode 没有 `/goal`，也没有"目标达成"事件。

| 文档要求 | 本插件的做法 |
| --- | --- |
| 触发条件：harness 报告目标达成 | 目标模式：工作流先让主 agent 完成目标，主 agent 节点正常结束即为目标达成。积累模式：由 hooks 在一轮或会话结束时、或由用户手动启动（第 16 节）。 |
| 子任务看不到主任务的任何产物（约束 3） | 子任务 agent `cv-subtask` 的提示里只有需求。它的工具调用由 hook 一律拦截并记录，记录不为空时这次运行无效（细则 5.3）。 |
| 对齐 agent 读代码、使用环境中的工具 | 对齐 agent `cv-align`，带读、写、搜索、shell 工具，在快照中工作。 |
| 公式生成、命题检查、运行检查、写报告 | 工作流中的 Python 节点，不交给模型。 |
| 需求的累加和纠正（"别的机制"） | hooks：`user_prompt_submit` 记录用户消息；`after_turn`、`session_end` 判断是否触发。hooks 只能运行命令，所以由命令行工具 `cv` 中的启动器在快照里启动工作流进程。 |

细则 2.1　插件由以下几部分组成：
- 工作流文件夹 `cross-validate/`，只能全局安装（细则 5.1）；
- agent 配置 `cv-subtask.yaml`、`cv-align.yaml`，装到 `~/.chrys/agents/`，iCode 只从用户目录读取 agent 配置；
- hooks 条目，合并进全局 `~/.chrys/hooks/hooks.yaml`，`id` 都以 `cv-` 开头；
- 命令行工具 `cv`，子命令为 `install`、`init`、`new`、`check`、`status`、`uninstall`。

插件不使用 skills 和 MCP。

细则 2.2　三个模型可以分别配置：主 agent、子任务 agent、对齐 agent。建议给子任务配一个与主 agent 不同的模型，这是文档五元组表中改进 pₛ⁻ 的办法（换来源）。

## 3 状态目录

细则 3.1　插件的一切状态都放在项目之外：`~/.chrys/cross-validate/projects/<项目键>/`，权限为 700。项目键是项目真实路径的 SHA-256 前 16 位，加上目录名。项目中不写入任何东西。理由：主 agent 能读写项目，它不应读到命题和报告，也不应能改写需求记录（细则 16.6、第 18 节）。

```
projects/<项目键>/
  project.json            项目路径、启用时间、设置（cv init 写入）
  ledger/<需求编号>.jsonl  需求记录（第 15 节）
  ledger/current          当前需求编号，一行文本
  lock                    运行锁（细则 16.3）
  pending                 待办标记（细则 16.3）
  running                 正在运行的启动器的进程号（细则 16.3）
  runs/<run>/             每次运行的全部产物，见下表
  reports/<run>.md        报告副本；reports/latest.md 指向最新一份
snapshots/<run>/          快照，运行结束后默认删除（细则 16.4）
```

环境变量 `CV_CHRYS_HOME`（代替 `~/.chrys`）和 `CV_ICODE`（代替 `icode` 命令）只供测试使用。

细则 3.2　运行编号 `<run>` 的格式为 UTC 时间戳加 4 位随机十六进制数，例如 `20261029T151230Z-3fa2`。运行目录中的文件：

| 文件 | 写入者 | 内容 |
| --- | --- | --- |
| `run.json` | 启动器 | 模式、触发方式、项目路径、快照路径、代码版本、需求记录的范围 |
| `ledger.jsonl` | 启动器 | 这次用到的需求记录副本，已经过预处理（细则 15.3） |
| `requirement.json` | 程序 | R：每条的原话片段、整理后的句子、来源消息；每条消息的去向（细则 15.4） |
| `requirement.txt` | 程序 | R 的整理后文本，供切句 |
| `sentences.json` | 程序 | 切句与分类（第 6 节） |
| `subtask.txt`、`subtask-revised.txt` | 子任务 agent | 声明、清单、命题的原始输出及重写（第 7 节） |
| `propositions.json` | 程序 | 解析后的命题、公式语法树、检查结论（第 8 至 10 节） |
| `tool-violations.jsonl` | hook | 子任务 agent 的工具调用记录，正常应为空（细则 5.3） |
| `history-reads.jsonl` | hook | 被拦下的、访问状态目录的工具调用，只在全局目录中（细则 5.6） |
| `align/` | 对齐 agent | `checks.json` 及它写的脚本（第 11 节） |
| `traces/` | checker | 每次轨迹运行的轨迹、退出码、输出末尾（第 12 节） |
| `results.json` | checker | 每条检查的执行记录和结果（细则 13.6） |
| `w-before.json` | 程序 | 对齐开始前 W 中每个文件的摘要（细则 5.4） |
| `digests.json` | 程序 | 各阶段摘要的副本，供查阅；核对以工作流状态中的那一份为准（细则 5.2） |
| `report.md`、`report.json` | 程序 | 可信度报告（第 14 节） |

## 4 入口与流程

细则 4.1　工作流 `cross-validate` 的输入只有两种：

| 输入 | 模式 |
| --- | --- |
| 以 `@cv-run:` 开头，后接运行目录的绝对路径 | 积累模式。由启动器生成，工作流读取其中的 `run.json`。 |
| 其他任何文本 | 目标模式。这段文本是目标，同时就是需求 R。 |

用户可能在 TUI 里手动选中这个工作流，再输入一段恰好以 `@cv-run:` 开头的文字。这时运行目录要么不存在，要么不属于任何已启用的项目，工作流报错退出。

细则 4.2　**目标模式**：
- `implement` 节点由主 agent（默认 `Code`）完成目标；它失败或被中断、没有给出结果时不算目标达成，不做交叉验证，报告结论为无结论并说明原因。
- W 就是项目目录本身。主 agent 已经停止，交叉验证期间没有别人改动 W。
- 状态仍写在项目之外（细则 3.1），R 不经整理，每句的原话就是 R 本身。

细则 4.3　**积累模式**：W 是启动器做的快照（细则 16.4）。工作流先整理需求（`consolidate`），再做交叉验证。

细则 4.4　流程与算法 1 的对应：

| 算法 1 | 节点 | 执行者 |
| --- | --- | --- |
| 触发条件 | 目标模式：`implement`；积累模式：hooks 或 `cv check`（第 16 节） | 主 agent / 启动器 |
| （上游）整理最终需求 | `consolidate` → `consolidate_check`，不合格时 `consolidate_revise` 一次（第 15 节） | 子任务 agent → 程序 |
| 第 1 行 切句、分类 | `split` → `split_check`，不合格时 `split_revise` 一次 | 子任务 agent → 程序 |
| 第 2、3 行 翻译、推理 | `propose`（同一次调用） | 子任务 agent |
| 第 4 行 检查命题 | `propose_check`；不通过的送 `propose_revise` 重写一次，再检查一次 | 程序，重写由子任务 agent 完成 |
| 第 5 行 句子 → 公式 | `propose_check`（解析成功是检查通过的条件之一） | 程序 |
| 第 6 行 交给对齐 agent | `align` → `align_check`，格式不合法时 `align_revise` 一次 | 对齐 agent → 程序 |
| 第 7 行 运行检查 | `run_checks` | 程序（checker） |
| 第 8 行 写报告 | `report` | 程序 |

细则 4.5　实现算法 1 某一行的函数，用注释 `# 算法1 第N行` 标注。

细则 4.6　子任务 agent 每次调用都是新会话，提示里只有本节点需要的需求或前一步输出，以及固定的说明文字。

细则 4.7　节点超时。
- agent 节点按 `config.json` 设置超时。
- `run_checks` 的超时设为 `None`，由它自己的预算控制（细则 11.8）。
- 有副作用的节点不自动重试。

细则 4.8　**agent 没有回答，或程序节点出错。**
- agent 节点超时或出错、没有给出回答时，按这一阶段"重写后仍不合格"处理，不再重写：
  - 整理：运行停止；
  - 切句：程序兜底切句（细则 6.1）；
  - 命题：首次没有回答时运行停止；重写没有回答时，不通过的命题被丢弃；
  - 对齐：所有命题记为对齐失败（细则 11.6）。
- 报告注明是哪个节点没有回答。
- 检查节点、checker、报告节点自身出错时，运行停止，报告写明出错的节点和原因。报告节点出错时，输出一份只含结论"无结论"和原因的简短报告。程序节点不能因为 agent 的输出或轨迹的内容而崩溃。

## 5 安全边界

细则 5.1　**checker 必须是安装的那一份。**
- 项目中的同名工作流优先于全局工作流，而主 agent 能写项目，所以快照不复制 `.chrys/`（细则 16.4）。
- 启动器在快照目录中运行 `icode workflow list --json`，确认 `cross-validate` 来自全局目录，且其文件夹的摘要与 `cv init` 或安装时记录的一致，然后才启动。
- 目标模式下，工作流的第一个 Python 节点做同样的检查：工作流文件自身的路径必须在全局工作流目录中，且文件夹的摘要与安装时记在 `install.json` 中的一致；没有安装记录也不运行。

细则 5.2　**checker 的输入在运行期间不得改变。**
- 摘要保存在工作流的状态里（节点之间传递的值），不保存在运行目录中。对齐 agent 和检查命令都能写运行目录，却改不到工作流状态。`digests.json` 只是一份供查阅的副本。
- 冻结的内容：
  - 开始时：工作流文件夹；
  - `consolidate_check` 或 `after_implement` 之后：`requirement.json`、`requirement.txt`、`run.json`；
  - `propose_check` 之后：`propositions.json`；
  - `align_prompt`，即对齐 agent 开始之前：`w-before.json`；
  - `align_check` 之后：冻结的 `checks.json`，以及 `align/` 中当时的每个文件；
  - `run_checks` 之后：`results.json`。
- `run_checks` 开始前、结束后，以及 `report` 开始前，各复核一次。冻结的文件被修改或删除，`align/` 中原有的文件被修改或删除，都使报告无效，并写明是哪些文件。`align/` 中新增的文件（缓存、日志）只列出，不影响结论。
- 文件夹的摘要包括指向目录的符号链接（按链接目标记录），不包括 `__pycache__`：iCode 和对齐 agent 运行 Python 时会合法地写这些缓存，检查命令则不读它们（细则 5.5）。
- 对齐 agent 带 shell，能写它想写的任何地方。这条细则检测改动，不能阻止改动（第 18 节）。

细则 5.5　**检查命令不得留下进程。**
- 每次执行检查命令，都经过一个包装进程：它在新的进程组中运行 `sh -c`，命令结束或超时后，杀掉命令留下的全部后代进程，再返回。在 Linux 上，包装进程把自己设为子进程收养者（`PR_SET_CHILD_SUBREAPER`），脱离进程组的后代也会被收养并杀掉；其他系统只杀进程组（第 18 节）。
- 包装进程只保留标准输出和标准错误的末尾，checker 等待它的时间不超过检查的超时加 10 秒。
- 检查命令的环境变量另加 `PYTHONDONTWRITEBYTECODE=1`，以及指向一个新建空目录的 `PYTHONPYCACHEPREFIX`：检查中的 Python 既不写、也不读 W 和 `align/` 中的 `__pycache__`，事先放进去的字节码不起作用。
- 包装进程以 `python -I` 启动，它所在的目录不进入模块搜索路径。

细则 5.3　**子任务 agent 不得调用工具。**
- `cv-subtask.yaml` 不配置任何工具，并关闭 skills 的自动加载（`auto_load_user_agents_skills: false`、`auto_load_cwd_agents_skills: false`）。iCode 仍会给每个 agent 附上 `sleep` 和三个 skill 工具。
- 全局 hooks 中有一个阻断型 `before_tool_call` hook，`match` 限定为 `cv-subtask`。它拦下这个 agent 的任何工具调用，并把调用追加到运行目录的 `tool-violations.jsonl`。运行目录的路径由环境变量 `CV_RUN_DIR` 传入。
- 目标模式下工作流由用户在 iCode 中启动，iCode 进程里没有 `CV_RUN_DIR`。这时 hook 把调用追加到 `~/.chrys/cross-validate/tool-violations.jsonl`，每行带时间和 `cwd`；检查节点读取 `cwd` 与 W 相同、时间不早于本次运行开始的记录。
- 每个子任务节点之后的检查节点确认 `tool-violations.jsonl` 为空；不为空，这次运行无效。全局记录中缺少 `cwd` 的行无法归属，按时间对所有运行都算数（宁可误判为无效）；hook 取不到载荷中的 `cwd` 时，记下它自己的工作目录。

细则 5.6　**agent 不去读其他运行的结果。** 状态目录里有历史运行的命题、检查脚本和报告，主 agent 和对齐 agent 读到它们，就不再是独立的一次检查，"报告对主 agent 不可见"也会落空。
- 全局 hooks 中有三个阻断型 `before_tool_call` hook，用 `match.args` 分别匹配工具的 `path`、`command`、`working_dir` 参数，只有提到状态目录时才触发，平常的工具调用不启动任何进程。
- 提到状态目录的调用一律拦下，只有两种例外：`cross-validate/bin/`（用户的 `cv` 命令）；对齐 agent 访问位于状态目录内的 W（积累模式的快照），以及尚未生成报告的运行中的 `align/`。
- 被拦下的调用记入 `history-reads.jsonl`（时间、`cwd`、profile、工具名）。工作目录是本次 W 的记录，算作这次运行的注写进报告，不影响结论：调用已被拦下，没有读到东西。
- 这只能挡住明说路径的访问，防的是 agent 自发去读，防不住有意绕过（例如 `cd ..`、拼接路径）。见第 18 节。子任务 agent 不受此节影响，它的任何工具调用都被拦下（细则 5.3）。

细则 5.4　**W 中原有的文件不得改变。**
- 对齐开始前，计算 W 中每个文件的摘要，写进 `w-before.json`，它的摘要随即按细则 5.2 冻结，对齐 agent 运行时已经改不了。
- `run_checks` 开始前、结束后和 `report` 开始前各复核一次：原有文件被修改或删除时，报告标为无效，并列出这些文件。`w-before.json` 缺失或被改动，同样无效。
- 新增的文件（构建产物、缓存、日志）只在报告中列出，不影响结论。
- 对齐 agent 的脚本写在运行目录的 `align/` 中，不写在 W 中。

## 6 切句与分类（第 1 行）

细则 6.1　子任务 agent 读 `requirement.txt`，输出 JSON 数组，每项是 `{"id": "S1", "text": "…", "labels": [...]}`。程序检查：
- `text` 是 R 的逐字片段；
- 各片段按顺序拼接、去掉空白后，与 R 去掉空白后相同。

不合格时送回修正一次。仍不合格时，由程序按句末标点（`。！？；` 和换行）切句，所有句子标为 `无`，报告注明"切句兜底：本次没有翻译命题"（细则 17.1）。

细则 6.2　分类标签取自第 2 行列出的五类：`规则`、`条件`、`数量约束`、`示例`、`接口规定`，可以有多个，不属于任何一类的标 `无`。带标签的句子要翻译，所有句子都参与推理。

细则 6.3　**原话。** 翻译依据的"原句"是用户的原话，不是整理后的句子。
- 积累模式下，`requirement.json` 中每条 R 都带有它的原话片段（细则 15.4）。句子 Sᵢ 在 `requirement.txt` 中有一个位置，与它重叠的那些 R 条目的原话片段，就是 Sᵢ 可引用的原话。
- 目标模式下，原话就是 Sᵢ 本身。

## 7 子任务输出的文本格式（第 2、3 行）

子任务 agent 输出三段纯文本：`声明`、`清单`、`命题`。贪吃蛇的例子：

```
声明
实体  蛇、食物、游戏
谓词  吃到(蛇, 食物)      这一步蛇头进入了食物所在的格子
      撞到自身(蛇)        这一步蛇头进入了蛇身所在的格子
      新生成(食物)        这一步生成了新的食物
      位于蛇身(食物)      食物所在的格子被蛇身占据
      移动(蛇)            这一步蛇头的位置发生了变化
      结束(游戏)          游戏处于结束状态
位置  头(蛇)              蛇头所在的格子
      尾(蛇)              蛇尾所在的格子
数量  长度(蛇)            蛇占据的格子数
      格子总数            游戏区域中的格子数

清单
存在            R1
状态            R2
不变式          R3、R6
动作的效果      R4
事件的后果      R5
边界            R10
终态            R7
最终会发生的事  R8
结构            R9

命题
编号  R4
来源  推理
依据  〔动作的效果〕吃到食物是蛇变长的方式
句子  只要 蛇 吃到 食物，下一步 蛇的长度 等于 蛇的长度 加 1
```

细则 7.1　**声明。** 每行由类别、名称、含义三部分组成，用两个以上的空格分隔；以空白开头的行沿用上一行的类别。

| 类别 | 说明 |
| --- | --- |
| `实体` | 可以用 `、` 一行列出多个，不写含义 |
| `谓词` | 至少一个参数（文档：谓词带上它所描述的对象），参数是已声明的实体 |
| `位置` | 取值不是数的项，参数为零个或多个实体 |
| `数量` | 取值是数的项，参数为零个或多个实体 |
| `动作` | 句式"从 S 出发，依次执行……"中的动作名 |
| `接口` | 需求中规定的接口名（函数、类型、模块、字段），名称必须逐字出现在 R 的原话中。可以用 `、` 一行列出多个，名称可以带反引号，不必写含义 |

名称的限制：
- 只由文字、字母、数字和下划线组成（Unicode 的单词字符），不以数字开头，不以"下划线加数字"结尾（与下标 `_k` 冲突）；
- 不能是单个拉丁字母（与变量和时序算子冲突），也不能是 `R`、`M` 这类公式记法用到的名字；
- 不能是保留字（细则 8.8）；
- 不能写成"`不` 或 `没有` 加另一个已声明的谓词"，否则粘连写法 `a 不p` 有两种读法（细则 8.3）；
- 可以含 `的`，"a的f"怎样切分，见细则 8.2。

细则 7.2　**清单。** 推理清单的九项每项一行，后列命题编号；一项没有命题时写 `无：` 加理由。缺一项即不合格。列出的编号必须是本次输出中的命题编号。

输出中断时，报告中断本身，而不是一串“编号不存在”。下列情况判定为输出中断：缺少 `命题` 段；或者清单列出的编号不存在，同时最后一个命题块缺字段，或者不存在的编号都大于写出的最大编号。程序拿不到模型的结束原因，这是从文本作出的判断。原因写在错误列表最前面，提示重写时少写几条，并提示检查模型配置的 `max_output_tokens`（思考和答案共用这个上限）。

细则 7.3　**命题。** 每条命题是一个块，块之间空一行；块内每行是"字段名、两个以上空格、值"。
- 程序容忍常见的装饰：字段名两侧的 `**`，字段名后的 `：` 或 `:`，行首的 `- `。
- 一个块读不出编号时，它不会被忽略：它作为一条"无编号"的命题，列入不通过的命题，原因是"读不出编号"，随其他不通过的命题送回重写（细则 9.3）。

| 字段 | 规则 |
| --- | --- |
| 编号 | `R` 加序号，本次输出中唯一 |
| 来源 | `翻译` 或 `推理` |
| 依据 | 翻译：用 `「…」` 引用原话，引文必须是某个带标签句子可引用原话（细则 6.3）的逐字片段。推理：以 `〔清单项〕` 开头接理由，清单项是九项之一，并与清单段一致。需求没有规定、选了一种读法的推理命题，在清单项之后紧接 `〔需求未说明〕`，再写明需求没说什么、按哪种读法处理（细则 13.8）。翻译命题不能这样标。 |
| 句子 | 套用第 8 节句式的受控句子 |
| 公式 | 只在未套用句式时由子任务填写，写作 `未套用句式：` 加第 10 节记法的公式。套用句式的命题不写，公式由程序生成。 |

## 8 受控句式的文法（第 5 行：句子 → 公式）

文档要求每个句式唯一对应一个公式，由程序机械生成。下面的文法保证：一个句子要么只有一种解析结果，要么解析失败。

细则 8.1　**词法。**
- 词与词之间用空格分隔（与文档示例一致），`，` 只用来分隔句式的从句。
- 括号写 `（）` 或 `()`。
- 字面量：
  - 数用 ASCII 数字写的十进制，可以带负号和小数点，不带多余的前导零，整数部分不超过 30 位；全角数字、上标等其他写法不是数，句子解析失败；
  - 字符串用 `「…」`；
  - 列表、对象、`true`、`false`、`null` 用 JSON 写法；从 `[` 或 `{` 开始，读到配对的括号为止，算作一个词。
- 变量是单个小写拉丁字母，可以带一位数字，例如 `x`、`y1`。
- 代码中的名字用反引号括起来，例如 `` `Point` ``，只出现在结构句式和 `调用` 中。
- 句末的 `。` 可有可无。

细则 8.2　**项。**

| 写法 | 含义 |
| --- | --- |
| `a的f` | 一元位置或数量 f(a)，例如 `蛇的长度` → 长度(蛇)。名称中含 `的` 时，按声明尝试所有切分，恰有一种合法才接受，否则报歧义。 |
| `f` | 零元位置或数量，例如 `格子总数` |
| `f(a, b)` | 函数写法，任何元数都可用 |
| 实体名 | 作参数时指该实体唯一的个体（细则 12.4） |
| 变量、字面量 | 原样保留 |
| `E 加/减/乘/除 E` | 算术。乘除优先于加减，同级从左到右，可加括号 |

细则 8.3　**原子命题。**

| 写法 | 公式 |
| --- | --- |
| `a p`、`a p b` | 谓词的自然写法 → p(a)、p(a, b) |
| `p(a, b)` | 函数写法 |
| `x 是 T`、`x 不是 T` | T(x)、¬T(x)，T 是实体 |
| `a 不 p`、`a 没有 p` | ¬p(a)。粘连写法 `a 没有p`、`a 不p` 在词法阶段拆开 |
| `E1 等于/不等于/小于/大于/不小于/不大于 E2` | `= ≠ < > ≥ ≤` |

细则 8.4　**状态命题。** P、Q 由原子命题组合而成，不含时序算子。优先级从高到低：
1. `不`：前缀，作用于函数写法的原子或括号；
2. `并且`；
3. `或者`；
4. `如果 P 那么 Q`：P → Q，不用逗号。

可以加括号。

细则 8.5　**句式表。** 程序按开头的关键词和从句结构选句式，与文档句式表一一对应。

| 类 | 句式 | 公式 |
| --- | --- | --- |
| 具体事实 | ``调用 `f`(v, …) 得到 v`` | f(v, …) = v，f 须声明为接口，参数和结果为字面量 |
| | ``调用 `f`(v, …) 失败`` | 失败(f(v, …)) |
| | `初始时 v 等于 c` | v₀ = c |
| | 状态命题 | 原样 |
| 一般性质 | `总是 P` | G P |
| | `从不 P` | G ¬P |
| | `只要 P，就 Q` | G(P → Q) |
| | `只要 P，下一步 Q` | G(P → N(Q))，N 见细则 8.6 |
| | `只要 P，最终 Q` | G(P → F Q) |
| | `一旦 P，此后一直 P` | G(P → G P)，两处 P 解析结果相同 |
| | `在 Q 之前，不会 P` | ¬P W Q |
| | `存在一个 T x，使 P`；`存在一个 x，使 P` | ∃x:T P；∃x P |
| | `恰好存在一个 T x，使 P` | ∃!x:T P |
| | `对所有 T x，P`；`对所有 x，P` | ∀x:T P；∀x P |
| | `下一步 Q` | N(Q) |
| | `从 S 出发，依次执行 a1、…、an，之后 Q` | S₀ ∧ 动作₀ = a1 ∧ … ∧ 动作ₙ₋₁ = an → Qₙ（时间约定见细则 12.2），动作须已声明。Q 也可以写 ``调用 `f`(v, …) 得到 v`` 或 ``调用 `f`(v, …) 失败``，表示执行完这些动作之后再做这次调用；这样的命题只能用 command 检查 |
| 结构 | ``代码中存在 类型/函数/模块 `N` `` | 存在(N) |
| | ```N` 的签名是 「…」`` | 签名(N) = 「…」，按文本比较 |
| | ```N` 包含 字段/方法 `x` `` | 包含(N, x) |
| | ```M` 调用 `N` ``、``…不调用…`` | 调用(M, N)、¬调用(M, N) |
| | ``只有 `M` 修改 D`` | 只由(M, D)，D 是代码名或已声明的位置、数量（不能是实体或动作） |
| | `代码中存在表示 C 的元素` | 表示(C)，C 是已声明的名称或项 |

结构句式中的代码名都必须声明为接口（细则 7.1），所以只能出现需求中规定的名字。需求没有规定接口时，只能用 `代码中存在表示 C 的元素`（文档推理清单第 9 项）。

细则 8.6　**下一步。**
- `下一步 Q` 读作"下一个状态满足 Q，其中比较式右边的项取这一个状态的值"。这与文档示例 R4 的公式 `长度(蛇)′ = 长度(蛇) + 1` 一致：左边取下一步的值，右边取这一步的值。
- 程序生成的形式 N(Q) 是：
  - Q 中没有比较式时，就是 `X Q`；
  - 否则先把 Q 中的 `不` 推到原子上（`不 (P 并且 Q)` 变成 `不 P 或者 不 Q`，`如果 P 那么 Q` 变成 `不 P 或者 Q`，比较式的否定换成相反的比较符号），再把每个文字 ℓ（原子或带 `不` 的原子）换成 `X ℓ`，每个比较式 `L op R` 换成 `L′ op R`。
  - 比较式的左边不含状态的项（只有字面量）时，`L′` 没有意义，整个比较式换成 `X (L op R)`，即两边都取下一步的值。
- 这样，`下一步 a 等于 b` 与 `下一步 a 不等于 b`、`下一步 不 (P 并且 Q)` 与 `下一步 不 P 或者 不 Q` 的时间语义都相同。
- `X` 和 `′` 的求值见细则 10.3。

细则 8.7　**量词。**
- 量词句式只出现在句子最外层，P 是状态命题。
- 带类型的量词 `x:T` 的论域是 T 的个体。不带类型时，x 只能出现在 `x 是 T` 这类原子中；出现在其他任何位置（谓词或项的参数、比较式、算术）都因类型不明不通过检查。
- 需要量词与时序算子嵌套时，用未套用句式。

细则 8.8　**保留字。** 句式和文法用到的词都是保留字，不能作为声明的名称：

```
的 是 不 没有 并且 或者 如果 那么 等于 不等于 小于 大于 不小于 不大于 加 减 乘 除
总是 从不 只要 就 下一步 最终 一旦 此后一直 在 之前 不会 存在一个 恰好存在一个 对所有 使
从 出发 依次执行 之后 调用 得到 失败 初始时 代码中存在 签名是 包含 字段 方法 类型 函数 模块
不调用 只有 修改 表示 元素 存在 签名 只由 动作 不是 true false null
```

细则 8.9　**测试。** 每个句式至少有一个"句子 → 公式"的测试。文档贪吃蛇的十条命题全部作为测试，其中 R6、R8、R9 的写法按细则 17.2 调整。

## 9 命题检查（第 4 行）

细则 9.1　逐项检查，任何一项不满足即不通过：
1. 字段齐全，取值合法（细则 7.3）。
2. 句子能按第 8 节解析；或者注明了未套用句式，而公式能按第 10 节解析。句子能套用句式时，不得再写公式（文档：套不进任何句式的命题才直接写公式），否则公式可能与句子不符。
3. 只使用已声明的名称，参数个数与类型一致，变量都被量词约束。结构谓词的参数个数固定：`存在`、`表示` 一个，`签名`、`包含`、`调用`、`只由` 两个；`存在`、`包含`、`调用` 的参数是代码名。谓词不能当作项用在比较式和算术中。
4. 不含实现上的名字。
   - 句子和公式中形如 ASCII 标识符、长度不小于 2 的词，除了 `「」` 中的字符串、JSON 字面量中的字符串、变量和下标 `_k`，都必须逐字出现在 R 的原话中。
   - 反引号中的代码名必须声明为接口。
5. 翻译命题：
   - 引文合法（细则 7.3）。依据中的 `「…」` 可以嵌套，按配对的括号读出引文。
   - 句式要有引文中的关键词或句子的标签作依据（文档翻译第 1 至 3 条）。关键词只用来允许句式，不用来禁止，所以引文中偶然出现的字（例如"时间"中的"时"）不会挡住合法的翻译：

     | 句式 | 依据 |
     | --- | --- |
     | `总是` | 引文含 总是、始终、一直、永远 之一，或句子带 `规则`、`条件`、`数量约束` 标签 |
     | `从不` | 引文含 不能、不得、不可、不会、不允许、禁止、从不、永不 之一 |
     | `只要…就` | 引文含 如果、时（"初始时"除外）、当、每当、只要、若 之一，或句子带 `规则`、`条件`、`数量约束` 标签 |
     | `只要…下一步`、`只要…最终` | 同上，或引文含 之后、后、然后、最终 之一 |
     | `一旦…此后一直` | 引文含 一旦、此后、从此、之后一直 之一 |
     | `在…之前，不会…` | 引文含 之前、以前、直到 之一 |
     | `调用…得到`、`调用…失败`、`从 S 出发` | 句子带 `示例` 标签 |
     | 结构句式 | 句子带 `接口规定` 标签 |
     | 其余（具体事实、`初始时`、量词句式、`下一步`） | 不需要依据 |

     `从不` 不看标签：否定词是它唯一的依据，所以"不需要界面"不能译成"从不 有界面"。有多段引文时，任一段提供依据即可。未套用句式的命题不受此限（文档：套不进任何句式的命题直接写公式）。
   - 引文中的异常名（以 `Error` 或 `Exception` 结尾的 ASCII 标识符，例如 `IndexError`）要保留：它必须出现在句子或公式中，或者出现在命题用到的谓词、项的名称或含义中。把"抛出 IndexError"抽象成"报错"之后，抛出别的异常的错误代码也能通过。引文不止说这一件事时，只引用相关的部分。
   - 引文所在句子带 `示例` 标签时，公式中的每个数（包括 JSON 字面量中的数）都要在引文里以相同的值出现（翻译第 2 条：示例照原样保留数值，不做推广）。例外是 `从 S 出发` 的 S：它只选出示例所说的那些运行，不断言任何结果，原话又常常不写起始状态（"依次 push(1)、push(2) 后"没有说栈一开始是空的），所以只查 Q 中的数。S 写错时没有轨迹满足前件，这条命题是对齐失败（细则 12.5），不会变成通过。引文中的数按值读出：阿拉伯数字、全角数字和简单的中文数字（例如"十二""两百"）都算，`10` 中的 `1` 不算 1。
6. 推理命题的清单项合法，并与清单段一致。标了 `〔需求未说明〕` 的，之后要有说明；翻译命题不能标（细则 7.3）。
7. 编号唯一。
8. 依赖状态的命题要说明时间。没有时序算子、也没有下标的公式只在第一个状态上判定（细则 10.4、13.1）。这样的公式含有带参数的谓词或项时（实体判断 `x 是 T` 和参数全是字面量的除外），不予通过：`∀v:值 弹出(栈, v) → 栈顶(栈) = v` 在第一个状态上几乎必然成立，错误的代码也能通过。说初始情况写 `初始时`，说任何时刻写 `总是`、`只要`，需要量词时写 `未套用句式：∀x:T G(…)`。这与文档一致：具体事实"不含谓词和量词，只涉及具体的值"。零个参数的数量和位置（例如 `格子总数 等于 100`）不受此限。

细则 9.2　声明与清单的检查：
- 类别合法；
- 名称不重复、不是保留字；
- 参数都是已声明的实体；
- 接口名逐字出现在原话中；
- 清单覆盖九项，列出的编号都存在。

细则 9.3　不通过的命题连同原因送回子任务 agent 重写一次，重写后再检查一次。仍不通过的被丢弃，报告中列为"未通过检查"并写明原因，不交给对齐 agent。声明或清单不合格时，整段输出送回重写一次；仍不合格，这次运行停止，报告写明原因。

只重写命题时，合并的规则是：
- 第一次通过检查的命题保留，重写中同号的命题不予理会；
- 其余编号以重写为准：重写中出现的编号（包括把重复的编号改成新号、给读不出编号的块补上的编号），取重写中的全部同号命题，替换第一次的同号命题；
- 读不出编号的块，在重写给出了新编号时被替换，否则保留为不通过；不通过的命题，句子原样出现在重写的某个新编号下时，视为被改了编号，丢掉旧的那条（例如两条 R1 中的一条改成了 R2，另一条就不再重复）；其余不通过而重写中没有出现的编号，保留为不通过；
- 清单取两次输出的并集，让改了编号的推理命题能在清单中找到；
- 重写中新增的声明照细则 9.2 检查，不合格的不加入，原因写进报告；
- 合并后的全部命题再按细则 9.1 检查一次。

细则 9.4　"一条命题只说一件事"无法机械判断，只在提示中要求（第 18 节）。

## 10 公式记法与语义

细则 10.1　**记法**沿用文档：
- 逻辑联结词 `¬ ∧ ∨ →`；
- 时序算子 `G F X U W`；
- 量词 `∃ ∃! ∀`，带类型时写作 `∃x:T`；
- `′`（下一状态的值）；
- `₀…₉` 下标（第 k 个状态的值）；
- 比较 `= ≠ < > ≤ ≥`，算术 `+ − × ÷`；
- 谓词和项用函数写法，代码名用反引号。

解析时也接受 ASCII 写法：`! & | -> <= >= != - * /`、`_k` 下标、`'`。

优先级从高到低：`¬`、一元时序算子、`∧`、`∨`、`U`/`W`（右结合）、`→`（右结合）。量词的作用范围延伸到最右。`′` 和下标只能加在项和原子上。

细则 10.2　**语法树。** 公式存为 JSON 语法树，每个节点是 `{"op": …, "args": [...]}`：

| 类 | op |
| --- | --- |
| 联结词 | `not`、`and`、`or`、`implies` |
| 时序 | `G`、`F`、`X`、`U`、`W` |
| 量词 | `exists`、`exists1`、`forall`，带 `var` 和可选的 `type` |
| 比较 | `eq`、`ne`、`lt`、`gt`、`le`、`ge` |
| 算术 | `add`、`sub`、`mul`、`div` |
| 原子与项 | `pred`、`term`，带 `name` |
| 其他 | `var`、`const`（实体名作常量，带 `name`）、`lit`（带 `value`）、`next`（′）、`at`（下标，带 `k`）、`call`、`fails`、`struct`（带 `kind`：exists、signature、contains、calls、only、represents） |

`动作` 是一个特殊的项 `{"op": "term", "name": "动作", "args": []}`，取轨迹状态的 `动作` 字段；动作名写作字符串字面量。

打印出的公式再解析一遍，必须得到同一棵树；测试检查这一点。

细则 10.3　**下一步的两种形式。**
- 公式中的 `X` 按弱下一步解释：轨迹在当前状态结束时，`X φ` 推定为真。这是文档"只要求坏事不发生的命题，没发现违反时得到推定为真"的要求（细则 17.3）。
- `′` 可以加在比较式中的任何项上，也可以加在原子上。含 `′` 的比较式定义为 `X (比较式′)`：带 `′` 的项取下一状态的值，不带 `′` 的项取当前状态的值。例如 `L′ op R` 就是 `X (L op c)`，c 是 R 在当前状态的值。`′` 不能叠用。原子上的 `′`，即 `p(a)′`，就是 `X p(a)`。
- 不带 `′` 的项涉及的个体在当前状态不存在时，比较式按细则 12.3 在下一状态为假，它的否定在下一状态为真；轨迹在当前状态结束时，仍按弱、强下一步取真、假。
- 求值前先做这一改写，再转成否定范式（NNF）。否定经过弱下一步时，变成它的对偶强下一步（¬X̄φ ≡ X(¬φ)，强下一步在轨迹结束时推定为假）；否定经过 G、F、U、W 时，按对偶规则变成 F、G、R、M。
- 强下一步、R、M 只出现在内部的否定范式中，不出现在打印的公式里。

细则 10.4　**命题的类**按语法树判断，不看名称：

| 类 | 判断方式 |
| --- | --- |
| 结构命题 | 含 `struct` 节点 |
| 时序命题 | 含 `G F X U W` 或 `next` 节点 |
| 具体事实 | 其余 |

## 11 对齐 agent 与检查清单（第 6 行）

文档对对齐 agent 的输出"不作规定"。本节只规定 checker 读取检查的接口，不限制对齐 agent 怎样绑定、选什么形态。

细则 11.1　对齐 agent 的输入（文档：命题集、主任务的代码、环境中的工具）：
- 声明；
- 通过检查的命题（编号、来源、句子、公式）；
- W 的路径；
- `align/` 的路径；
- 本节的格式说明。

它的输入里没有需求 R，也没有翻译命题引用的原话（细则 17.4）。

细则 11.2　对齐 agent 写出 `align/checks.json`：

```json
{
  "bindings": {"长度(蛇)": "snake.py 中 Snake.body 的长度", "结束(游戏)": "game.py 中 Game.over"},
  "checks": [
    {"proposition": "R9", "form": "结构检查", "kind": "command",
     "command": "python \"$CV_ALIGN/r9_structure.py\"", "timeout": 60},
    {"proposition": "R4", "form": "插桩加模糊测试", "kind": "trace",
     "command": "python \"$CV_ALIGN/run_snake.py\"", "runs": 50, "timeout": 120}
  ]
}
```

| 键 | 含义 |
| --- | --- |
| `bindings` | 每个声明名称绑定到代码中的什么，文字说明，写进报告 |
| `form` | 形态名称，只写进报告 |
| `kind` | `command` 或 `trace`，决定执行方式和结果的取值 |
| `unstated_inputs` | 可选，布尔值，默认 false。为 true 时这项检查用的是需求没有规定的输入或局面，结果只列给人确认（细则 13.8） |

`align/` 中不得有符号链接：链接的目标在冻结之后仍能改动（细则 5.2）。有链接时按格式不合法处理（细则 11.7）。

细则 11.3　**command 检查。**
- 在 W 中以 `sh -c` 执行一次，环境变量为 `CV_ALIGN`（`align/` 的路径）和 `CV_W`。
- 退出码 0 为通过；1 为失败，标准输出的最后 2000 个字符作为反例；其他退出码、无法启动、超时，都是对齐失败。
- 结果只有通过和失败两种。

细则 11.4　**trace 检查。**
- 执行 `runs` 次，第 i 次设置 `CV_RUN=i`（从 0 开始，供命令作随机种子）和 `CV_TRACE`（轨迹文件路径）。
- 命令把轨迹写到 `CV_TRACE`（第 12 节），由 checker 在轨迹上判定公式（第 13 节）。
- 时序命题得四值之一，具体事实得通过或失败。结构命题不能用 trace 检查。

细则 11.5　**每条时序命题至少要有一条 trace 检查**，command 检查只作补充。这样时序命题的结论来自 checker 对程序生成的公式的判定，而不是来自对齐 agent 所写脚本的退出码。缺少 trace 检查，算对齐失败。

细则 11.6　**对齐失败。** 以下情况都算对齐失败，结果记为失败（对齐）：
- 一条命题没有任何检查，或者只有 `unstated_inputs` 的检查；
- 检查格式不合法；
- 时序命题缺少 trace 检查；
- 轨迹缺少公式要用的值；
- "从 S 出发"型命题没有一条轨迹满足其前件（细则 12.5）；
- 对齐 agent 没有回答（细则 4.8）。

细则 11.7　**格式修正。** `checks.json` 不能解析或格式不合法时，把错误送回对齐 agent 修正一次。仍不合法时，所有命题按对齐失败处理。修正只涉及格式，不告诉对齐 agent 任何检查结果。

**冻结前试跑。** `checks.json` 格式合法后、冻结之前，程序把每个不同的 trace 命令各运行一次（`CV_RUN=0`，轨迹写到临时目录，总共不超过 300 秒），在轨迹上试判定用到它的命题，只收集轨迹本身的问题：缺键、`实体` 写法不对、值的类型不对、没有写出轨迹。有问题时和格式错误一样送回修正一次，修正后不再试跑，遗留的问题在检查时算对齐失败。试判定的结果一律丢弃，退出码非 0、超时的运行也不说明原因：这些可能是代码的缺陷，对齐 agent 知道了，可能把检查改到通过为止。试跑不算检查，不影响结论。试跑本身出错时跳过。

细则 11.8　**资源上限**写在 `config.json` 中：

| 设置 | 默认值 |
| --- | --- |
| 每条检查的超时 | 120 秒，`timeout` 不得超过 |
| `runs` 的上限 | 200 |
| 每条轨迹的状态数上限 | 10000，超出截断并注明 |
| 整次 `run_checks` 的预算 | 3600 秒 |

预算用尽后，尚未运行的检查记为失败（对齐），原因写"预算用尽，未运行"。一条 trace 检查只运行了一部分时，它的结果是已运行部分的结果与失败（对齐）中较差的一个，原因写"预算用尽，只运行了 i 次"：已经发现的违反照常报告，没有发现违反也不算通过。

`checks.json` 中的命令不得含空字符（NUL），否则格式不合法。

细则 11.9　checker 自己执行命令，不采信对齐 agent 报告的任何结果。执行的是冻结时的 `checks.json`（细则 5.2）。

细则 11.10　**检查要严格，也要测得到。** 下面两点写在对齐提示中。程序只能查出其中一部分（细则 13.7），其余属于第 18 节所说的"检查本身可能写错"。
- 严格按声明的接口名检查。接口不存在时命题不成立（退出码 1），不换别的名字代替：需求要的是 `size()`，`length()` 不算。
- 命题或声明中写了具体的异常类型时，只认这个类型，不用 `except Exception` 一概而论。
- 事件按调用记录，不按效果记录：这一步调用了 `push(x)`，"压入"就为真，不管元素有没有真的进去。按效果记录时，丢元素的错误代码会被记成"这一步没有压入"，命题全都成立，等于自己证明自己。
- 数量和位置优先用需求规定的接口观察：需求规定了 `size()`，长度就取它的返回值，不直接读内部列表，否则 `size()` 写错也查不出来。
- trace 脚本只记录观察到的事实，不自己判定对错。代码的行为不符合预期时照实记录，继续运行或正常结束；只有脚本无法继续时才以非 0 退出。脚本提前退出时，所有用它的命题都记为失败，看不出究竟违反了哪一条，结论也不再来自 checker 对公式的判定（细则 11.5）。
- 随机输入不回避难的情况：把规模推到明显超过示例，允许重复的值，走到边界。不要为了好判定而把输入限制在特殊情况里，每条命题的前件都要真的发生。
- 只走正常使用能到达的状态：通过代码的公开入口驱动程序，不直接改内部字段造出正常使用到不了的局面；需求没有规定的参数取使程序有意义的值。需求没有说怎么办的输入（例如 0 格的区域）放进带 `unstated_inputs` 的检查（细则 13.8）。实测中脚本把食物放到蛇身上、用 0 格和 1 格的棋盘，正确的代码因此被判违反。
- "代码中存在表示 C 的元素"看含义，不看名字：变量、字段、返回值、条件判断都可以表示 C，在 `bindings` 中写明是哪一个；只有找不到任何能区分 C 的东西时才不成立。实测中检查脚本在代码里找名为"撞墙"的元素，正确的代码因此失败。

## 12 轨迹格式与时间约定

细则 12.1　一条轨迹是 JSON Lines 文件，每行一个状态：

```json
{"实体": {"蛇": ["蛇"], "食物": ["f1"]},
 "值": {"长度(蛇)": 3, "头(蛇)": [4, 2], "尾(蛇)": [2, 2], "格子总数": 100,
        "吃到(蛇,食物)": false, "撞到自身(蛇)": false, "结束(游戏)": false,
        "新生成(食物)": false, "位于蛇身(f1)": false, "移动(蛇)": true},
 "动作": "右"}
```

细则 12.2　**时间约定。** 第 i 个状态记录：
- 时刻 i 的值：位置、数量，以及描述状态的谓词；
- 从时刻 i 到 i+1 这一步中发生的事件谓词（文档声明中"这一步……"的谓词），以及这一步执行的 `动作`。

事件写在发生之前的那一行，与变化前的值放在一起。实测中有一轮的脚本把事件写到之后那一行，"吃到食物"和变长后的长度落在同一行，8 条"只要……下一步……"的命题在正确的代码上被判确定违反。这种错误的轨迹格式完全合法，试跑查不出来（细则 11.7），所以对齐提示给出一个两行的例子，并要求对齐 agent 交答案前自己核对一行事件为真的轨迹。

第 0 个状态是开始时刻，由对齐 agent 决定从哪里开始（例如游戏开局之后）。最后一个状态没有后续的一步，它的事件谓词由对齐 agent 按"这一步没有发生"填写。

按这个约定：
- R4"吃到食物，下一步长度加一"：吃到(蛇, 食物) 在状态 i 为真，表示从 i 到 i+1 这一步吃到了，因此要求长度在 i+1 等于 i 时的长度加一；
- "从 S 出发，依次执行 a1…an，之后 Q"：S 在状态 0 成立，动作₀…动作ₙ₋₁ 依次为 a1…an，Q 在状态 n 成立。

细则 12.3　**值的写法。**
- 键是去掉空白的函数写法，参数是实体名（细则 12.4）或个体编号。
- 谓词的值是布尔值，数量的值是数，位置的值是任意 JSON 值，按 JSON 相等比较。
- 每个状态都要给出公式用到的全部键，缺失算对齐失败。缺失出现在结果已经确定（细则 13.2 第 4 步）的状态之后时，保留已经确定的结果：先报缺陷（细则 13.3）。
- 参数中的个体不在本状态的 `实体` 中时，这个原子为假，含它的比较式也为假。
- 两个整数按精确值比较；有一个不是整数时，按差的绝对值不超过 1e-9 比较。

细则 12.4　**实体名作常量。**
- `实体` 中每个实体对应一个列表，列表的元素是字符串或数（个体编号），否则算对齐失败。
- 在轨迹的某个状态的 `实体` 中出现过的实体，是"列出的实体"。列出的实体作参数时，指它在本状态中唯一的个体。本状态中它没有个体时（例如食物被吃掉、还没有生成），含它的原子和比较式为假，与细则 12.3 对不在场个体的规定一致；有多个个体时算对齐失败。这个个体在键中写编号或写实体名都可以：`"实体": {"栈": ["S"]}` 时，`栈顶(S)` 和 `栈顶(栈)` 指同一个值，两个都有时取编号的那个。
- 从未列出的实体只有一个个体，编号就是实体名本身，总是存在。
- 量词在求值的那个状态上取 `实体` 中列出的个体。

细则 12.5　**"从 S 出发"型命题。** 只在动作序列与句子完全相符的轨迹上判定。没有一条轨迹相符时，算对齐失败；否则在相符的轨迹上判定，结果取最差。

细则 12.6　**截断与异常。**
- 命令超时、异常退出时，已写出的轨迹仍按有限前缀判定。超时时最后一行可能只写了一半：没有换行结尾、又不能解析的最后一行被丢掉，结果注明截断。
- 轨迹文件必须是普通文件（不是符号链接、管道或设备），一行不超过 1 MB，整个文件不超过 `max_trace_bytes`（默认 100 MB），超出部分截断并注明。行不是 UTF-8、不是 JSON 对象、嵌套过深，都算对齐失败。
- 退出码非 0 时，这次运行的结果是失败（检查），报告写出退出码、标准错误和标准输出的末尾，已写出的轨迹不再判定（失败已是最差的结果）。程序崩溃或检查脚本出错，都算作交叉验证没有通过（文档：对齐 agent 出错同样算作交叉验证失败）。
- 轨迹中的 `NaN`、`Infinity` 不是 JSON 值，算对齐失败。
- 轨迹为空时，算对齐失败。

## 13 判定（第 7 行）

细则 13.1　时序命题在一条轨迹上的结果取四值之一，定义来自 RV-LTL（Bauer、Leucker、Schallhart 2010，文档 [28]）：

| 结果 | 含义 |
| --- | --- |
| 确定违反 | 前缀之后无论怎样继续（包括就此结束），命题都不成立 |
| 推定为假 | 还不确定；按有限轨迹语义，前缀本身不满足命题 |
| 推定为真 | 还不确定；按有限轨迹语义，前缀本身满足命题 |
| 确定成立 | 前缀之后无论怎样继续（包括就此结束），命题都成立 |

"怎样继续"指有限的继续，与第 5 步的有限轨迹语义一致。所以确定的结果与推定的结果不会矛盾：确定违反的前缀，推定也为假。

细则 13.2　**算法。**
1. 按细则 10.3 改写 `′`，并转成否定范式。
2. 量词在求值的状态上展开为所列个体的合取或析取。
3. 用公式推进（progression）逐个状态改写公式，并用等价规则化简。下一状态的义务保留弱、强之分：弱下一步的 ⊥ 和强下一步的 ⊤ 都不化简，因为轨迹在此结束时，前者为真、后者为假。
4. 结果为 ⊥ 时是确定违反，为 ⊤ 时是确定成立，并记下是在哪一个状态确定的。
5. 否则用有限轨迹语义在最后一个状态上求值：弱下一步、G、W、R 取真；强下一步、F、U、M 取假。真为推定为真，假为推定为假。
6. 非时序命题在第 0 个状态求值，结果为通过或失败。

化简只用等价规则，所以报告为"确定"的结果一定是确定的；但一个实际已经确定的结果，可能只被报告为推定（第 18 节）。

细则 13.3　**结果的顺序**（用于取最差），从差到好：

> 失败（检查）＝ 确定违反 ＜ 失败（对齐）＜ 推定为假 ＜ 推定为真 ＜ 确定成立 ＜ 通过

- 发现缺陷的结果（失败（检查）、确定违反）排在"检查不了"（失败（对齐））之前，免得一个真实的反例被对齐失败盖掉。
- 一条命题在多次运行、多条检查上的结果取最差（文档：多次运行取最差）。报告同时列出每条检查各自的结果。
- 覆盖不足（细则 11.6 前三项）作为这条命题的一个"失败（对齐）"参与取最差，不替换已有检查的结果。所以一条检查发现的失败，不会被"缺少 trace 检查"盖掉。

细则 13.4　**反例。**
- 轨迹检查：写出运行序号、确定或推定的那个状态的序号、到该状态为止的最后 5 个状态；有动作时，写出完整的动作序列。
- command 检查：写出标准输出的末尾。
- 程序异常退出：写出运行序号、退出码和标准错误的末尾。它与轨迹上的确定违反同样差，先出现的保留，不被后来较好的反例替换。

细则 13.5　**可监控性。** 否定范式中含 F、U、M 或强下一步的时序命题（活性成分），在有限运行上通常得不到确定违反。量词只看它在否定范式中实际出现的那一种极性（`∃!` 展开后两种都有）。报告中给这类命题加标记，说明它们的推定为假只是没有观察到，不是发现了违反。

细则 13.6　`results.json` 中每条检查一项，包括：命题编号、`kind`、命令、每次运行的退出码、耗时、轨迹文件及其摘要、结果、反例。

细则 13.7　**没有被检验的命题。** 形如 `G(P → …)`（外层可以有全称量词）、P 不含时序算子的命题，如果 P 在一条命题的所有轨迹、所有状态、所有个体上都没有成立过，它的通过只是空真。报告在这条命题后注明"前件从未成立，实际没有被检验"，统计中列出这类命题的数量。结果和结论不变：有些命题的前件本来就不该成立（例如"只要 深度 小于 0"），不能据此判失败。P 无法在轨迹上求值时不作判断。

细则 13.8　**需要人确认的结果。** 两类结果照常求出、写进报告，但不计入比对结论，也不参与命题结果的取最差：
- 标了 `〔需求未说明〕` 的推理命题（细则 7.3）。它的结果仍是这条命题的结果，在 `results.json` 中带 `"unstated": true`。
- 带 `unstated_inputs` 的检查（细则 11.2）。命题的结果只取其余检查的最差；这些检查的结果另列在 `results.json` 中这条命题的 `unstated_inputs` 下。

报告在"需要人确认"一节列出其中结果为失败、确定违反、失败（对齐）或推定为假的项，写明依据和反例（细则 14.1）。理由同细则 14.2：文档建模的前提是"代码正确且子任务都成功时一定通过"。需求没有规定的地方，命题选了一种读法，代码选了另一种，并不说明代码错了，也不说明子任务错了；计为未通过，这个前提就不成立。实测中三轮贪吃蛇都把正确的代码判为未通过，原因都在这一类：蛇头走进正要腾空的尾格算不算撞到自身、0 格的棋盘怎样处理。

## 14 可信度报告（第 8 行）

细则 14.1　`report.md` 沿用文档"检查与判定"一节示例的格式，从上到下依次为：
1. **需求**：R 的每一条整理后的句子，后附原话片段和来源消息编号。积累模式下另列被判为非需求、已被更正、已撤销的消息，还要列出 R 中同时出现在 W 代码里的 ASCII 名字，标为"疑似来自实现"（细则 15.3）。目标模式下 R 就是用户输入的原文，不会混入实现上的名字，不列。
2. **代码**：项目的提交号；有未提交改动时注明"含未提交改动"，并给出改动的摘要；不是 git 仓库时，给出文件摘要。积累模式下注明快照时间和触发方式。
3. **命题**：每条一行，写出编号、来源、结果、形态、反例。结果相同、编号相邻的可以合并，例如 `R1 至 R3`。活性命题加标记（细则 13.5）。有运行超时、轨迹被截断或预算用尽时，在说明中写出次数。
4. **未通过检查**：被丢弃的命题及原因（细则 9.3）。
5. **需要人确认**：细则 13.8 的项，没有时省略。
6. **绑定**：来自 `checks.json`。
7. **统计**：
   - 提交给检查的命题中，翻译、推理、未套用句式的数量（文档要求）；
   - 其中被丢弃的数量；
   - 各种结果的数量；
   - 前件从未成立的命题数量（细则 13.7）；
   - 需求未说明的命题数量、超出需求的输入的检查数量（细则 13.8）。
8. **比对结论**：见细则 14.2。有需要人确认的项时，注明项数。
9. **说明**：报告是概率凭证；只有满足文档式 (7) 时，通过检查的代码精确率才高于基准正确率。报告不判断式 (7) 是否成立。

`report.json` 包含同样的内容。

报告中引用的程序输出、绑定说明、形态名称都来自不可信的来源，写进报告时压成一行，并替换掉 `|`、`*`、`#`、反引号，使它们无法伪造报告的结构。

细则 14.2　**比对结论**对应文档第 2 章的事件 A，取下列之一：

| 结论 | 条件 |
| --- | --- |
| 无效 | 细则 5.2、5.3、5.4 中任何一条不满足 |
| 无结论 | 没有命题进入检查，或被丢弃的命题超过提交总数的一半（`max_discard_ratio`，默认 0.5） |
| 比对未通过 | 至少一条命题的结果是失败或确定违反，需求未说明的命题除外（细则 13.8） |
| 比对通过 | 其余情况 |

推定为假不计入"未通过"，但在报告中单独列出：文档只说推定为真是安全性质应有的通过结果，没有说推定为假算不通过；而文档建模的前提是"代码正确且子任务都成功时一定通过"，把有限运行上的推定为假计为未通过，会让这个前提不成立。

细则 14.3　工作流的最终输出就是 `report.md` 的内容。积累模式下，启动器把它复制到 `reports/<run>.md`，并更新 `reports/latest.md`。

## 15 需求积累（文档所说的"别的机制"）

细则 15.1　**启用。** 插件只在用户用 `cv init` 启用过的项目中工作。
- `cv init` 拒绝在家目录、根目录启用。
- 不是 git 仓库的项目，要加 `--allow-non-git` 才能启用。项目目录被上层仓库的 `.gitignore` 忽略时，也按不是 git 仓库处理。
- hooks 从会话的工作目录向上查找，找到的第一个启用过的目录就是项目。所以在项目的子目录里启动的会话也会记录。
- 找不到启用过的目录时，hooks 立即退出，什么都不做。

细则 15.2　**记录。**
- 阻断型 `user_prompt_submit` hook（很快，`on_error: warn`，保证在 `after_turn` 之前写完）把用户提交的文本追加到当前需求记录。
- iCode 交给这个 hook 的只有用户提交的文本，主 agent 的回复不会进入记录。
- 以下情况不记录：
  - 以 `/` 开头的消息；
  - 载荷中 `session_kind` 为 `workflow`；
  - 环境变量 `CV_INTERNAL=1`（插件自己启动的运行）。
- 记录每行一条：`{"id": "M3", "time": "…", "session": "…", "injected": false, "text": "…"}`。编号在一份记录内递增。追加时持有记录的文件锁。

细则 15.3　**预处理。** 用户可能把代码、报错、主 agent 的回复或交叉验证报告粘贴进对话。这些内容属于主任务的产物，交给子任务就违反约束 3。启动器复制记录时：
- 以下内容替换为 `〔已省略：粘贴的代码或日志〕`：
  - 围栏代码块（```` ``` ```` 或 `~~~`）；
  - 形似堆栈的行（`Traceback`、`at …:行号`、`File "…", line`）；
  - 绝对路径和含 `/` 的相对路径。只有一个 `/` 的词（例如 `src/utils`），要两边都是长度不小于 2 的 ASCII 名字，或者有一边带扩展名，才算路径，免得 `km/h`、`和/或` 这类写法被替换；
- 含有报告标记（报告第一行的固定标题 `交叉验证可信度报告`）的消息整条省略，去向固定为非需求；
- 被替换的位置记在 `ledger.jsonl` 中，报告列出受影响的消息编号。

接口名属于需求（文档：需求规定的接口名除外），所以 ASCII 名字不剥离；R 中同时出现在 W 代码里的名字，在报告中列出供用户核对。

细则 15.4　**整理。** `consolidate` 节点由子任务 agent 读预处理后的记录（编号与原文，按时间顺序），输出：

```json
{"requirement": [
   {"text": "下单时总价满 200 元减 30 元。",
    "quotes": [{"from": "M2", "text": "满 100 元减 20 元"}, {"from": "M5", "text": "改成满 200 减 30"}]}],
 "messages": {"M1": "需求", "M2": "已被更正", "M3": "非需求", "M5": "更正 M2", "M6": "撤销 M4", "M4": "已被更正"}}
```

消息的去向：

| 去向 | 含义 | 是否必须被 R 引用 |
| --- | --- | --- |
| `需求` | 给出需求 | 是 |
| `补充` | 追加需求 | 是 |
| `更正 Mk` | 修改先前的 Mk | 是 |
| `撤销 Mk` | 删除先前的 Mk 中的需求 | 否 |
| `已被更正` | 被后来的更正或撤销完全取代 | 否；必须有一条后来的消息以 `更正` 或 `撤销` 指向它 |
| `非需求` | "继续""跑一下测试"、闲聊等 | 否 |

程序检查：
- 每条消息恰好一个去向；
- `Mk` 早于引用它的消息；
- 必须被引用的消息至少被 R 的一条引用；
- R 的每条至少有一个原话片段，片段是所注消息的逐字子串；
- R 整理后的句子中形如 ASCII 标识符的词，都出现在它的原话片段中。

不合格时送回重写一次；仍不合格时，这次运行停止，报告写"需求整理不合格"及原因。

`requirement.txt` 是各条整理后的句子按顺序连接而成的文本。翻译的依据引用原话片段，不引用整理后的句子（细则 6.3）。

细则 15.5　**每次都从原话整理。** 每次运行都从完整的记录重新整理，不在上一次的 R 上修改，避免文档引言所说的规范漂移。

细则 15.6　**新需求。** `cv new` 开始一份新的需求记录，并把 `ledger/current` 指向它。旧记录保留。

## 16 触发、启动器与快照

细则 16.1　**触发方式。** 三种，都针对当前需求记录：

| 触发 | 条件 | 设置 |
| --- | --- | --- |
| 手动 | `cv check` | — |
| 一轮结束 | `after_turn` 且 `status` 为 `ok`，并且自上次运行以来新记录的消息不少于 N 条 | `auto.enabled`，默认开启；`auto.min_new_messages`，即 N，默认 3 |
| 会话结束 | `session_end`，载荷不是工作流会话，并且自上次运行以来有新消息 | `auto.on_session_end`，默认开启 |

会话结束时的那一次最接近最终需求；之前的运行是中间结果，报告注明触发方式。中途触发属于对文档的偏离，见细则 17.5。

细则 16.2　**启动器**是 `cv` 中的函数，hooks 以分离模式（`fire_and_forget` 加 `detach`）调用它，`cv check` 直接调用它。它依次：
1. 取锁（细则 16.3）；
2. 复制并预处理需求记录（细则 15.3），写出 `run.json`；
3. 做快照（细则 16.4）；
4. 校验工作流来源（细则 5.1）；
5. 在快照目录中运行 `icode workflow run cross-validate --trust --input "@cv-run:<运行目录>"`，环境变量为 `CV_INTERNAL=1` 和 `CV_RUN_DIR`；
6. 复制报告；
7. 删除快照；
8. 释放锁；
9. 有待办标记就再来一次（细则 16.3）。

第 2 步之后任何一步出错（包括读不了项目中的某个文件），这次运行停止，报告写明原因，`run.json` 照常记下看过的消息，下一次触发不会因同一条消息反复出错。

细则 16.3　**锁与待办。**
- 每个项目一把锁：启动器对 `lock` 加 `flock`，并在整个运行期间持有。进程退出时锁自动释放，没有进程号复用的问题。
- 每次触发先写 `pending`，再取锁；拿不到锁就退出。`pending` 为空文件，存在即表示有待办。
- 拿到锁的启动器先删掉 `pending`，再运行。运行结束、释放锁之后，如果 `pending` 又出现了，就再去取锁：拿到了，并且记录中有这次运行没有看到的消息，就再运行一次；拿不到，说明另一个启动器已经拿到锁，由它处理。这保证最后一条消息总会被检查。
- 持锁期间，启动器把自己的进程号写在 `running` 中，`cv status` 据此判断是否正在运行，不去试探锁。
- "上次运行以来的新消息"按 `runs/` 中最近一次 `run.json` 记录的最后一条消息编号计算。

细则 16.4　**快照。**
- 位置是 `~/.chrys/cross-validate/snapshots/<run>/`。
- **复制范围。**
  - git 项目：复制 `git ls-files --cached --others --exclude-standard` 列出且确实存在的文件，子模块用 `git ls-files --recurse-submodules --cached` 补全。
  - 非 git 项目：复制全部文件。
  - 两种情况都排除 `.git/`、`.chrys/`，以及 `snapshot.exclude` 中的目录。
- **依赖目录。** `snapshot.link` 中列出的目录（例如 `node_modules`、`.venv`）以硬链接副本接入快照：目录结构重新建立，文件用硬链接，不复制内容，也不计入上限。检查在快照中新建、删除、替换文件，都不会影响项目；只有原地改写已有文件会改到项目（第 18 节）。快照与项目不在同一个文件系统时，退回符号链接，并在报告中注明。`snapshot.copy` 中列出的被忽略文件（例如 `.env`）照常复制。两者都在报告中注明。
- **符号链接。** 指向项目内部的相对链接按链接复制，包括指向目录的链接；其他链接不复制，在报告中列出。这一条不管依赖目录：依赖目录本身是符号链接时不接入快照，在报告中注明。git 列出却找不到的文件（例如文件名无法解码）也在报告中注明。
- **上限。** 文件数默认 20000，字节数默认 500 MB；超过时这次运行停止，报告写明原因。
- **一致性。** 复制前后各计算一次源文件的摘要，不一致时重新复制，最多 3 次；仍不一致时，这次运行停止。
- **代码版本。** 记下提交号和未提交改动的摘要。查询时用 `git --no-optional-locks`，不刷新项目的 `.git/index`，也不抢 `index.lock`。
- **清理。** 快照只保留最近 `keep_snapshots` 份（默认 0，即运行结束后删除）；每次启动时也清理以前被中断的运行留下的快照。运行目录保留最近 20 次（`keep_runs`）。

细则 16.5　**hooks 的过滤。** 所有 `cv-` hooks 在以下情况下立即退出：
- 项目未启用；
- `CV_INTERNAL=1`；
- 载荷 `session_kind` 为 `workflow`。

这样插件自己启动的工作流结束时，不会再次触发。用户自己运行的其他工作流，也不会触发交叉验证。

细则 16.6　**报告不交给主 agent。** 报告只写在状态目录中，`cv status` 和 `cv check` 只显示结论和报告路径，不显示报告内容，免得主 agent 通过 shell 调用它们读到报告。显示的结论取自程序记录的 `report.json`，不从报告正文中摘取，因为正文会引用被检查程序的输出。插件不向主 agent 注入任何内容。主 agent 带 shell，技术上能读到状态目录；插件不在项目中留下任何指向它的路径，并在第 18 节说明。

细则 16.7　**安装与卸载。**
- `cv install` 安装以下几样：
  - 把工作流复制到 `~/.chrys/workflows/cross-validate/`，并记录文件夹摘要；
  - 把两个 agent 配置复制到 `~/.chrys/agents/`；
  - 在 `~/.chrys/hooks/hooks.yaml` 中追加 `cv-` 条目，不改动已有条目。
- 安装后运行 `icode hook validate` 和 `icode workflow validate cross-validate`。
- iCode 首次加载 agent 配置时会改写文件、补上 id，所以安装和卸载按配置的 `name` 识别，不按字节比对。
- `cv uninstall` 只删除插件自己的条目和文件。
- hooks 文件的合并：
  - 插件的条目放在一对标记行之间，安装和卸载只改动标记之间的内容；`hooks.json` 按插件自己的四个 `id` 识别，不碰用户自己以 `cv-` 开头的条目。标记行不成对（文件被手动改过）、有不止一个 `hooks` 键、`hooks` 键的写法认不出时，不改动文件，说明原因。保留文件原来的换行符（CRLF 或 LF）。
- `cv install` 只能在插件仓库中运行；安装后的 `cv` 不能重新安装自己，在动任何文件之前就拒绝。
  - 合并先在内存中完成。`hooks:` 下的列表可以缩进也可以不缩进，后面可以有别的顶层键和注释；文件为空或没有 `hooks:` 时补上。遇到无法安全合并的写法（例如行内的非空列表 `hooks: [...]`），在改动任何文件之前就停下，说明原因。
  - 路径按 JSON 字符串的写法转义后填进 YAML。
  - 改动前把原文件备份为 `<文件名>.cv-backup`；原文件已含插件条目时不覆盖已有备份。合并后 `icode hook validate` 不通过，而原文件原本通过时，恢复原文件。
  - 卸载后列表为空时写作 `hooks: []`，保证文件仍然合法；卸载同时删除备份和 `install.json`。hooks 文件清理不了时，什么都不卸载，说明原因：只删掉工作流而留下 hooks，会让 hooks 指向不存在的命令。

## 17 与文档的偏离和对文档示例的调整

细则 17.1　**切句兜底。** 文档规定由子任务 agent 切句，本插件也是。只有它两次都切不对时，才由程序按标点切句；这时所有句子标为 `无`，本次没有翻译命题，报告注明。理由：不让整次交叉验证因为一次切句错误而无法进行。

细则 17.2　**示例句子的写法。** 文档的 R6、R9 按本文法要改写，公式不变：

| 命题 | 文档写法 | 本文法写法 |
| --- | --- | --- |
| R6 | 食物 不 位于 蛇身 上 | 食物 不 位于蛇身 |
| R9 | 代码中存在表示蛇的长度的元素 | 代码中存在表示 蛇的长度 的元素 |

R8 的"游戏 没有结束"在词法阶段自动拆开（细则 8.3），不需要改写。R6 的写法无法与声明 `位于蛇身(食物)` 机械对应。

细则 17.3　**下一步取弱语义。** RV-LTL 原文的有限轨迹语义把 X 作为强下一步。本插件按文档正文"只要求坏事不发生的命题，没发现违反时得到推定为真"，把公式中的 X 作为弱下一步，它的否定才是强下一步（细则 10.3）。否则，轨迹恰好停在"吃到食物"那一步时，R4 这类安全性质会得到推定为假。

RV-LTL 原文的"确定"针对无限的继续；本插件的"确定"针对有限的继续，包括就此结束（细则 13.1），这样确定与推定使用同一种有限轨迹语义，不会互相矛盾。

细则 17.4　**示例报告中的"通过"。** 文档示例报告把时序命题 R2 至 R4 写作"通过"，而正文规定时序命题取四值之一。本插件以正文为准：时序命题必须有 trace 检查，结果取四值之一（细则 11.5）。同样的代码，本插件报告 R2 至 R4 的结果通常是推定为真。

细则 17.5　**中途触发。** 文档把交叉验证定位为一次性的收尾检查。按用户的要求，本插件在需求积累到一定程度时也会触发（细则 16.1）。为了不破坏文档建模中"主任务与子任务各生成一次、比对一次"的独立性，中途的报告和命题不交给主 agent，也不放在项目里（细则 3.1、16.6）。

细则 17.6　**R 是整理过的需求。** 文档协议的输入是"最终需求原文"。积累模式下，原文分散在多条消息中，并且相互更正。本插件把整理后的句子交给切句，同时保留逐字的原话片段，翻译只引用原话（细则 6.3、15.4），使"翻译照字面、引用原句"仍然成立。

细则 17.7　**`动作`、`接口` 两类声明。** 文档的声明示例中没有这两类，而句式"从 S 出发，依次执行……"、`调用 f(a)` 和结构句式需要它们（细则 7.1）。

细则 17.8　**推定为假不计入未通过，被丢弃过多时为无结论。** 文档没有规定这两点，理由见细则 14.2。

细则 17.9　**放宽了翻译的依据。** 文档说规则、条件和数量约束"按关键词选句式"，没有说没有关键词时怎么办。实测中"空栈调用 pop() 抛出 IndexError"这样的规则句没有任何关键词，它的直译被丢弃，只能靠推理命题补。本插件让这些标签本身也能作 `总是`、`只要…` 的依据（细则 9.1 第 5 项）。代价是模型更容易把自己的理解当作翻译，译得过强时要到检查阶段才暴露。

细则 17.10　**状态命题要说明时间。** 文档句式表有 `对所有 x，P(x)`，没有说 P 依赖状态时在哪个时刻判定。本插件只在第一个状态判定这类公式，所以要求写明时间（细则 9.1 第 8 项）。

细则 17.11　**需要人确认的结果不计入结论。** 文档的结论只有比对通过和未通过，没有"需求没有规定"这一类。本插件让子任务把需求没有规定的读法标出来，让对齐 agent 把需求没有规定的输入单独列出，它们的结果只列给人确认（细则 13.8）。代价是：标得太多时，真实的错误也会只列给人看，不让结论变成未通过；对齐 agent 可以把难的情况放进带标记的检查，避开结论（第 18 节）。

## 18 局限

文档已经指出的：
- 交叉验证不能确保子任务产物与需求的语义一致，只让通过检查的代码与需求对齐的概率更高。
- 同一个模型读偏同一段需求时，查不出这类错误。办法是给子任务配置另一个模型（细则 2.2）。
- 对齐 agent 绑定错误、翻译错误，都算作交叉验证失败。

本实现另有的：
- **需求整理由模型完成。** 整理错了，主任务和子任务会一起错。报告列出原话片段和来源消息，供用户核对。
- **自动触发是启发式的。** 它不知道需求是否已经稳定，只有会话结束时的那次最接近最终需求。`session_end` 在会话回滚到开头、被删除时也会触发，这时会多运行一次。
- **记录的消息可能被撤回。** hook 记下消息之后，用户仍可能撤回这次输入；记录里会留下一条主 agent 没有看到的消息。
- **预处理只认得出常见形式。** 它识别不了的代码或日志仍会进入记录（细则 15.3）。
- **没有沙箱。** 插件能检测改动（细则 5.2、5.4），不能阻止。主 agent 和对齐 agent 都带 shell，以用户的权限运行，技术上可以读写状态目录，也可以改写全局安装的工作流和它的 `install.json`、`__pycache__`。细则 5.1 防的是项目中的同名工作流和安装后的改动，防不住有意改写 `~/.chrys` 的进程。
- **读取历史结果只拦得住明说路径的。** 目标模式下工作流跑在用户启动的 iCode 进程里，插件没有办法给 agent 套操作系统级的沙箱，只能看工具调用的参数（细则 5.6）。`cd ..`、拼接路径、脚本内部读文件都拦不住。要真正隔离，需要用户自己在 bwrap 这类沙箱里运行 iCode。
- **iCode 会把工作目录告诉每个 agent。** iCode 在每个 agent 的上下文中附上工作目录的路径。目标模式下，子任务 agent 因此能看到项目的路径（看不到内容）；积累模式下它看到的是快照目录的路径。
- **快照挡不住绝对路径。** 代码中的绝对路径可能让检查读写原项目，快照对此无能为力。依赖目录是硬链接副本，检查原地改写其中已有的文件，会改到项目里的同一个文件。
- **残留进程只在 Linux 上能全部清掉。** 其他系统上，检查命令中脱离进程组的后台进程可能活过检查（细则 5.5），之后再改动 W 或运行目录。对齐 agent 自己的 shell 留下的后台进程不经过包装进程，插件管不到；它们造成的改动，在报告开始前的复核中能被发现，报告写完之后的改动则发现不了。
- **有些要求程序检查不了。** "一条命题只说一件事"、"不推测代码如何实现"只在提示中要求。实现上的名字只能识别 ASCII 标识符，中文写的实现名词识别不了。
- **"确定"可能被低估。** 四值判定中，"确定"只依据化简得出，一个实际已经确定的结果可能被报告为推定。活性命题在有限运行上通常只能得到推定（细则 13.5）。
- **"需要人确认"可能被滥用。** 子任务看不到代码和结果，没有理由多标 `〔需求未说明〕`，但可能标错；对齐 agent 看得到代码，可以把会失败的情况放进带 `unstated_inputs` 的检查。程序只能要求每条命题另有不带标记的检查（细则 11.6），判断不了标记是否合理，报告列出所有被标记的失败供人复核。
- **检查本身可能写错。** 检查命令由对齐 agent 编写。checker 保证执行的是冻结的检查、结果不来自转述，不保证检查本身写对了，这正是文档模型中的 β。
- **没有空实现对照。** 文档的约束 1（子任务产物要能发现实际会犯的错误）需要在空实现或桩上运行检查才能经验地估计，本插件不做这一步。

## 附：安装与使用

本节不是细则，只说明怎样用。

```
./cv install                 # 安装工作流、两个 agent 配置和 cv- hooks，并运行 iCode 的校验
cd <项目> && cv init         # 在项目中启用需求积累与自动触发
cv check                     # 立即运行一次交叉验证
cv status                    # 最新结论和报告路径
cv new                       # 开始一份新的需求记录
cv uninstall
```

不启用积累模式时，也可以直接以目标模式运行：`icode workflow run cross-validate --input "<目标>"`。

需要在 iCode 中配置模型；建议给 `config.json` 的 `subtask_model` 配一个与主 agent 不同的模型（细则 2.2）。

本地模型写一次命题可能要十几分钟，模型配置要放宽两项，否则答案会被截断，或者请求超时后不断重试、什么也产出不了：`max_output_tokens`（思考和答案共用，实测 32768 够用）和 `http_read_timeout`（默认 300 秒，建议 1800）。`config.json` 的 `agent_timeout` 默认 3600 秒。
论文贪吃蛇例子的测试见 `examples/snake/README.md`。

模型每轮写出的命题和检查都不同，单轮的结果说明不了什么。要判断一次改动是否有效，用 `scripts/live_eval.py` 跑几轮再看平均抓到率：每轮在 bwrap 隔离的新目录里完整跑一次工作流，然后把冻结的检查在 15 个改坏的栈上重放。需要 Linux、bwrap、iCode 和一份模型配置，一轮约 40 到 90 分钟，已跑完的轮次不会重跑。例子可以指定用积累模式：代码预先放在项目里，没有写代码这一步，变异版本才能从同一份代码产生。

```
python3 scripts/live_eval.py --example examples/stack --model-yaml model.yaml --out eval-out --rounds 3
```
