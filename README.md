# iCode 交叉验证插件：实现细则

本插件为 [openJiuwen/iCode](https://gitcode.com/openJiuwen/iCode) 实现 `交叉验证与组合验证.md`（draft v2，下称"文档"）第 2、3 章的**交叉验证**。

文档规定了做什么，很多地方没有规定怎么做。本文把这些地方逐条定下来，作为实现和核验的依据。

- 每条细则有编号（`细则 N.M`），`STANDARDS.md` 和 checker 按编号引用。
- 细则只补充文档。确有偏离的地方，集中列在第 17 节，逐条说明理由。
- 文档正文和它的例子不一致时，以正文为准，差异同样列在第 17 节。

本文经过一次独立审查，审查意见已经并入（见第 17、18 节）。

---

## 1 范围

细则 1.1　只实现第 3 章"交叉验证的落地"，第 2 章是它的依据。第 4 章组合验证（依赖—保证、前提推断）不实现，也不预留接口。

细则 1.2　交叉验证是收尾检查，只产出可信度报告（概率凭证），不阻止、不打回、不要求主 agent 修改代码。报告不交给主 agent（细则 16.6）。

细则 1.3　文档说"需求在过程中的累加和纠正，由别的机制处理"。本插件把这个机制做成交叉验证上游的独立部分，即第 15、16 节的**需求积累与触发**。交叉验证本身（第 4 至 14 节）只把整理出的 R 当作最终需求。

细则 1.4　不限定被检查代码的语言。所有检查都是"在工作区里运行一条命令"（第 11 节）。

## 2 在 iCode 中的形态

iCode 的扩展点有：工作流、agent 配置、hooks、skills、MCP、外部 ACP agent。iCode 没有 `/goal`，也没有"目标达成"事件。

| 文档要求 | 本插件的做法 |
| --- | --- |
| 触发条件：harness 报告目标达成 | 目标模式：工作流先让主 agent 完成目标，主 agent 节点正常结束即为目标达成。积累模式：由 hooks 在一轮或会话结束时、或由用户手动启动（第 16 节）。 |
| 子任务看不到主任务的任何产物（约束 3） | 子任务 agent `cv-subtask` 的提示里只有需求。它的工具调用由 hook 一律拦截并记录，记录不为空时这次运行无效（细则 5.3）。 |
| 对齐 agent 读代码、使用环境中的工具 | 对齐 agent `cv-align`，带读、写、搜索、shell 工具，在快照中工作。 |
| 公式生成、命题检查、运行检查、写报告 | 工作流中的 Python 节点，不交给模型。 |
| 需求的累加和纠正（"别的机制"） | hooks：`user_prompt_submit` 记录用户消息；`after_turn`、`session_end` 判断是否触发。hooks 只能运行命令，所以由命令行工具 `cv` 中的启动器在快照里启动工作流进程。 |

细则 2.1　插件由以下几部分组成：
- 工作流文件夹 `cross-validate/`，只能全局安装（细则 5.1）；
- agent 配置 `cv-subtask.yaml`、`cv-align.yaml`，装到 `~/.chrys/agents/`，iCode 只从用户目录读取 agent 配置；
- hooks 条目，合并进全局 `~/.chrys/hooks/hooks.yaml`，`id` 都以 `cv-` 开头；
- 命令行工具 `cv`，子命令为 `install`、`init`、`new`、`check`、`status`、`uninstall`。

插件不使用 skills 和 MCP。

细则 2.2　三个模型可以分别配置：主 agent、子任务 agent、对齐 agent。建议给子任务配一个与主 agent 不同的模型，这是文档五元组表中改进 pₛ⁻ 的办法（换来源）。

## 3 状态目录

细则 3.1　插件的一切状态都放在项目之外：`~/.chrys/cross-validate/projects/<项目键>/`，权限为 700。项目键是项目真实路径的 SHA-256 前 16 位，加上目录名。项目中不写入任何东西。理由：主 agent 能读写项目，它不应读到命题和报告，也不应能改写需求记录（细则 16.6、第 18 节）。

```
projects/<项目键>/
  project.json            项目路径、启用时间、设置（cv init 写入）
  ledger/<需求编号>.jsonl  需求记录（第 15 节）
  ledger/current          当前需求编号，一行文本
  lock                    运行锁（细则 16.3）
  pending                 待办标记（细则 16.3）
  runs/<run>/             每次运行的全部产物，见下表
  reports/<run>.md        报告副本；reports/latest.md 指向最新一份
snapshots/<run>/          快照，运行结束后默认删除（细则 16.4）
```

环境变量 `CV_CHRYS_HOME`（代替 `~/.chrys`）和 `CV_ICODE`（代替 `icode` 命令）只供测试使用。

细则 3.2　运行编号 `<run>` 的格式为 UTC 时间戳加 4 位随机十六进制数，例如 `20261029T151230Z-3fa2`。运行目录中的文件：

| 文件 | 写入者 | 内容 |
| --- | --- | --- |
| `run.json` | 启动器 | 模式、触发方式、项目路径、快照路径、代码版本、需求记录的范围 |
| `ledger.jsonl` | 启动器 | 这次用到的需求记录副本，已经过预处理（细则 15.3） |
| `requirement.json` | 程序 | R：每条的原话片段、整理后的句子、来源消息；每条消息的去向（细则 15.4） |
| `requirement.txt` | 程序 | R 的整理后文本，供切句 |
| `sentences.json` | 程序 | 切句与分类（第 6 节） |
| `subtask.txt`、`subtask-revised.txt` | 子任务 agent | 声明、清单、命题的原始输出及重写（第 7 节） |
| `propositions.json` | 程序 | 解析后的命题、公式语法树、检查结论（第 8 至 10 节） |
| `tool-violations.jsonl` | hook | 子任务 agent 的工具调用记录，正常应为空（细则 5.3） |
| `align/` | 对齐 agent | `checks.json` 及它写的脚本（第 11 节） |
| `traces/` | checker | 每次轨迹运行的轨迹、退出码、输出末尾（第 12 节） |
| `results.json` | checker | 每条检查的执行记录和结果（细则 13.6） |
| `digests.json` | 程序 | 各阶段的摘要（细则 5.2） |
| `report.md`、`report.json` | 程序 | 可信度报告（第 14 节） |

## 4 入口与流程

细则 4.1　工作流 `cross-validate` 的输入只有两种：

| 输入 | 模式 |
| --- | --- |
| 以 `@cv-run:` 开头，后接运行目录的绝对路径 | 积累模式。由启动器生成，工作流读取其中的 `run.json`。 |
| 其他任何文本 | 目标模式。这段文本是目标，同时就是需求 R。 |

用户可能在 TUI 里手动选中这个工作流，再输入一段恰好以 `@cv-run:` 开头的文字。这时运行目录要么不存在，要么不属于任何已启用的项目，工作流报错退出。

细则 4.2　**目标模式**：
- `implement` 节点由主 agent（默认 `Code`）完成目标；它失败或被中断时不算目标达成，工作流结束并说明原因。
- W 就是项目目录本身。主 agent 已经停止，交叉验证期间没有别人改动 W。
- 状态仍写在项目之外（细则 3.1），R 不经整理，每句的原话就是 R 本身。

细则 4.3　**积累模式**：W 是启动器做的快照（细则 16.4）。工作流先整理需求（`consolidate`），再做交叉验证。

细则 4.4　流程与算法 1 的对应：

| 算法 1 | 节点 | 执行者 |
| --- | --- | --- |
| 触发条件 | 目标模式：`implement`；积累模式：hooks 或 `cv check`（第 16 节） | 主 agent / 启动器 |
| （上游）整理最终需求 | `consolidate` → `consolidate_check`，不合格时 `consolidate_revise` 一次（第 15 节） | 子任务 agent → 程序 |
| 第 1 行 切句、分类 | `split` → `split_check`，不合格时 `split_revise` 一次 | 子任务 agent → 程序 |
| 第 2、3 行 翻译、推理 | `propose`（同一次调用） | 子任务 agent |
| 第 4 行 检查命题 | `propose_check`；不通过的送 `propose_revise` 重写一次，再检查一次 | 程序，重写由子任务 agent 完成 |
| 第 5 行 句子 → 公式 | `propose_check`（解析成功是检查通过的条件之一） | 程序 |
| 第 6 行 交给对齐 agent | `align` → `align_check`，格式不合法时 `align_revise` 一次 | 对齐 agent → 程序 |
| 第 7 行 运行检查 | `run_checks` | 程序（checker） |
| 第 8 行 写报告 | `report` | 程序 |

细则 4.5　实现算法 1 某一行的函数，用注释 `# 算法1 第N行` 标注。

细则 4.6　子任务 agent 每次调用都是新会话，提示里只有本节点需要的需求或前一步输出，以及固定的说明文字。

细则 4.7　节点超时。
- agent 节点按 `config.json` 设置超时。
- `run_checks` 的超时设为 `None`，由它自己的预算控制（细则 11.8）。
- 有副作用的节点不自动重试。

## 5 安全边界

细则 5.1　**checker 必须是安装的那一份。**
- 项目中的同名工作流优先于全局工作流，而主 agent 能写项目，所以快照不复制 `.chrys/`（细则 16.4）。
- 启动器在快照目录中运行 `icode workflow list --json`，确认 `cross-validate` 来自全局目录，且其文件夹的摘要与 `cv init` 或安装时记录的一致，然后才启动。
- 目标模式下，工作流的第一个 Python 节点做同样的检查：工作流文件自身的路径必须在全局工作流目录中。

细则 5.2　**checker 的输入在运行期间不得改变。** 以下摘要写进 `digests.json`：
- `consolidate_check` 之后：`requirement.json`、`requirement.txt`；
- `propose_check` 之后：`propositions.json`；
- `align_check` 之后：冻结的 `checks.json`，以及工作流文件夹。

`run_checks` 开始前和 `report` 开始前，各复核一次。不一致时，报告标为无效，并写明哪个文件被改动。对齐 agent 带 shell，能写它想写的任何地方，这条细则检测改动，不能阻止改动（第 18 节）。

细则 5.3　**子任务 agent 不得调用工具。**
- `cv-subtask.yaml` 不配置任何工具，并关闭 skills 的自动加载（`auto_load_user_agents_skills: false`、`auto_load_cwd_agents_skills: false`）。iCode 仍会给每个 agent 附上 `sleep` 和三个 skill 工具。
- 全局 hooks 中有一个阻断型 `before_tool_call` hook，`match` 限定为 `cv-subtask`。它拦下这个 agent 的任何工具调用，并把调用追加到运行目录的 `tool-violations.jsonl`。运行目录的路径由环境变量 `CV_RUN_DIR` 传入。
- 目标模式下工作流由用户在 iCode 中启动，iCode 进程里没有 `CV_RUN_DIR`。这时 hook 把调用追加到 `~/.chrys/cross-validate/tool-violations.jsonl`，每行带时间和 `cwd`；检查节点读取 `cwd` 与 W 相同、时间不早于本次运行开始的记录。
- 每个子任务节点之后的检查节点确认 `tool-violations.jsonl` 为空；不为空，这次运行无效。

细则 5.4　**W 中原有的文件不得改变。**
- 对齐开始前，计算 W 中每个文件的摘要。
- `run_checks` 开始前和结束后各复核一次：原有文件被修改或删除时，报告标为无效，并列出这些文件。
- 新增的文件（构建产物、缓存、日志）只在报告中列出，不影响结论。
- 对齐 agent 的脚本写在运行目录的 `align/` 中，不写在 W 中。

## 6 切句与分类（第 1 行）

细则 6.1　子任务 agent 读 `requirement.txt`，输出 JSON 数组，每项是 `{"id": "S1", "text": "…", "labels": [...]}`。程序检查：
- `text` 是 R 的逐字片段；
- 各片段按顺序拼接、去掉空白后，与 R 去掉空白后相同。

不合格时送回修正一次。仍不合格时，由程序按句末标点（`。！？；` 和换行）切句，所有句子标为 `无`，报告注明"切句兜底：本次没有翻译命题"（细则 17.1）。

细则 6.2　分类标签取自第 2 行列出的五类：`规则`、`条件`、`数量约束`、`示例`、`接口规定`，可以有多个，不属于任何一类的标 `无`。带标签的句子要翻译，所有句子都参与推理。

细则 6.3　**原话。** 翻译依据的"原句"是用户的原话，不是整理后的句子。
- 积累模式下，`requirement.json` 中每条 R 都带有它的原话片段（细则 15.4）。句子 Sᵢ 在 `requirement.txt` 中有一个位置，与它重叠的那些 R 条目的原话片段，就是 Sᵢ 可引用的原话。
- 目标模式下，原话就是 Sᵢ 本身。

## 7 子任务输出的文本格式（第 2、3 行）

子任务 agent 输出三段纯文本：`声明`、`清单`、`命题`。贪吃蛇的例子：

```
声明
实体  蛇、食物、游戏
谓词  吃到(蛇, 食物)      这一步蛇头进入了食物所在的格子
      撞到自身(蛇)        这一步蛇头进入了蛇身所在的格子
      新生成(食物)        这一步生成了新的食物
      位于蛇身(食物)      食物所在的格子被蛇身占据
      移动(蛇)            这一步蛇头的位置发生了变化
      结束(游戏)          游戏处于结束状态
位置  头(蛇)              蛇头所在的格子
      尾(蛇)              蛇尾所在的格子
数量  长度(蛇)            蛇占据的格子数
      格子总数            游戏区域中的格子数

清单
存在            R1
状态            R2
不变式          R3、R6
动作的效果      R4
事件的后果      R5
边界            R10
终态            R7
最终会发生的事  R8
结构            R9

命题
编号  R4
来源  推理
依据  〔动作的效果〕吃到食物是蛇变长的方式
句子  只要 蛇 吃到 食物，下一步 蛇的长度 等于 蛇的长度 加 1
```

细则 7.1　**声明。** 每行由类别、名称、含义三部分组成，用两个以上的空格分隔；以空白开头的行沿用上一行的类别。

| 类别 | 说明 |
| --- | --- |
| `实体` | 可以用 `、` 一行列出多个，不写含义 |
| `谓词` | 至少一个参数（文档：谓词带上它所描述的对象），参数是已声明的实体 |
| `位置` | 取值不是数的项，参数为零个或多个实体 |
| `数量` | 取值是数的项，参数为零个或多个实体 |
| `动作` | 句式"从 S 出发，依次执行……"中的动作名 |
| `接口` | 需求中规定的接口名（函数、类型、模块、字段），名称必须逐字出现在 R 的原话中 |

名称的限制：
- 不能含空白、括号、逗号、反引号、`「」`；
- 不能是保留字（细则 8.8）；
- 可以含 `的`，"a的f"怎样切分，见细则 8.2。

细则 7.2　**清单。** 推理清单的九项每项一行，后列命题编号；一项没有命题时写 `无：` 加理由。缺一项即不合格。

细则 7.3　**命题。** 每条命题是一个块，块之间空一行；块内每行是"字段名、两个以上空格、值"。

| 字段 | 规则 |
| --- | --- |
| 编号 | `R` 加序号，本次输出中唯一 |
| 来源 | `翻译` 或 `推理` |
| 依据 | 翻译：用 `「…」` 引用原话，引文必须是某个带标签句子可引用原话（细则 6.3）的逐字片段。推理：以 `〔清单项〕` 开头接理由，清单项是九项之一，并与清单段一致。 |
| 句子 | 套用第 8 节句式的受控句子 |
| 公式 | 只在未套用句式时由子任务填写，写作 `未套用句式：` 加第 10 节记法的公式。套用句式的命题不写，公式由程序生成。 |

## 8 受控句式的文法（第 5 行：句子 → 公式）

文档要求每个句式唯一对应一个公式，由程序机械生成。下面的文法保证：一个句子要么只有一种解析结果，要么解析失败。

细则 8.1　**词法。**
- 词与词之间用空格分隔（与文档示例一致），`，` 只用来分隔句式的从句。
- 括号写 `（）` 或 `()`。
- 字面量：
  - 数用十进制，可以带负号和小数点；
  - 字符串用 `「…」`；
  - 列表、对象、`true`、`false`、`null` 用 JSON 写法；从 `[` 或 `{` 开始，读到配对的括号为止，算作一个词。
- 变量是单个小写拉丁字母，可以带一位数字，例如 `x`、`y1`。
- 代码中的名字用反引号括起来，例如 `` `Point` ``，只出现在结构句式和 `调用` 中。
- 句末的 `。` 可有可无。

细则 8.2　**项。**

| 写法 | 含义 |
| --- | --- |
| `a的f` | 一元位置或数量 f(a)，例如 `蛇的长度` → 长度(蛇)。名称中含 `的` 时，按声明尝试所有切分，恰有一种合法才接受，否则报歧义。 |
| `f` | 零元位置或数量，例如 `格子总数` |
| `f(a, b)` | 函数写法，任何元数都可用 |
| 实体名 | 作参数时指该实体唯一的个体（细则 12.4） |
| 变量、字面量 | 原样保留 |
| `E 加/减/乘/除 E` | 算术。乘除优先于加减，同级从左到右，可加括号 |

细则 8.3　**原子命题。**

| 写法 | 公式 |
| --- | --- |
| `a p`、`a p b` | 谓词的自然写法 → p(a)、p(a, b) |
| `p(a, b)` | 函数写法 |
| `x 是 T`、`x 不是 T` | T(x)、¬T(x)，T 是实体 |
| `a 不 p`、`a 没有 p` | ¬p(a)。粘连写法 `a 没有p`、`a 不p` 在词法阶段拆开 |
| `E1 等于/不等于/小于/大于/不小于/不大于 E2` | `= ≠ < > ≥ ≤` |

细则 8.4　**状态命题。** P、Q 由原子命题组合而成，不含时序算子。优先级从高到低：
1. `不`：前缀，作用于函数写法的原子或括号；
2. `并且`；
3. `或者`；
4. `如果 P 那么 Q`：P → Q，不用逗号。

可以加括号。

细则 8.5　**句式表。** 程序按开头的关键词和从句结构选句式，与文档句式表一一对应。

| 类 | 句式 | 公式 |
| --- | --- | --- |
| 具体事实 | ``调用 `f`(v, …) 得到 v`` | f(v, …) = v，f 须声明为接口，参数和结果为字面量 |
| | ``调用 `f`(v, …) 失败`` | 失败(f(v, …)) |
| | `初始时 v 等于 c` | v₀ = c |
| | 状态命题 | 原样 |
| 一般性质 | `总是 P` | G P |
| | `从不 P` | G ¬P |
| | `只要 P，就 Q` | G(P → Q) |
| | `只要 P，下一步 Q` | G(P → N(Q))，N 见细则 8.6 |
| | `只要 P，最终 Q` | G(P → F Q) |
| | `一旦 P，此后一直 P` | G(P → G P)，两处 P 解析结果相同 |
| | `在 Q 之前，不会 P` | ¬P W Q |
| | `存在一个 T x，使 P`；`存在一个 x，使 P` | ∃x:T P；∃x P |
| | `恰好存在一个 T x，使 P` | ∃!x:T P |
| | `对所有 T x，P`；`对所有 x，P` | ∀x:T P；∀x P |
| | `下一步 Q` | N(Q) |
| | `从 S 出发，依次执行 a1、…、an，之后 Q` | S₀ ∧ 动作₀ = a1 ∧ … ∧ 动作ₙ₋₁ = an → Qₙ（时间约定见细则 12.2），动作须已声明 |
| 结构 | ``代码中存在 类型/函数/模块 `N` `` | 存在(N) |
| | ```N` 的签名是 「…」`` | 签名(N) = 「…」，按文本比较 |
| | ```N` 包含 字段/方法 `x` `` | 包含(N, x) |
| | ```M` 调用 `N` ``、``…不调用…`` | 调用(M, N)、¬调用(M, N) |
| | ``只有 `M` 修改 D`` | 只由(M, D)，D 是代码名或已声明的位置、数量 |
| | `代码中存在表示 C 的元素` | 表示(C)，C 是已声明的名称或项 |

结构句式中的代码名都必须声明为接口（细则 7.1），所以只能出现需求中规定的名字。需求没有规定接口时，只能用 `代码中存在表示 C 的元素`（文档推理清单第 9 项）。

细则 8.6　**下一步。**
- `下一步 Q` 读作"下一个状态满足 Q，其中比较式右边的项取这一个状态的值"。这与文档示例 R4 的公式 `长度(蛇)′ = 长度(蛇) + 1` 一致：左边取下一步的值，右边取这一步的值。
- 程序生成的形式 N(Q) 是：
  - Q 中没有比较式时，就是 `X Q`；
  - 否则把 Q 的每个文字 ℓ（原子或带 `不` 的原子）换成 `X ℓ`，每个比较式 `L op R` 换成 `L′ op R`。
- 这样，`下一步 a 等于 b` 与 `下一步 a 不等于 b` 的时间语义相同，只是比较符号不同。
- `X` 和 `′` 的求值见细则 10.3。

细则 8.7　**量词。**
- 量词句式只出现在句子最外层，P 是状态命题。
- 带类型的量词 `x:T` 的论域是 T 的个体。不带类型时，x 只能出现在 `x 是 T` 这类原子中，否则因类型不明不通过检查。
- 需要量词与时序算子嵌套时，用未套用句式。

细则 8.8　**保留字。** 句式和文法用到的词都是保留字，不能作为声明的名称：

```
的 是 不 没有 并且 或者 如果 那么 等于 不等于 小于 大于 不小于 不大于 加 减 乘 除
总是 从不 只要 就 下一步 最终 一旦 此后一直 在 之前 不会 存在一个 恰好存在一个 对所有 使
从 出发 依次执行 之后 调用 得到 失败 初始时 代码中存在 签名是 包含 字段 方法 类型 函数 模块
不调用 只有 修改 表示 元素 存在 签名 只由 动作
```

细则 8.9　**测试。** 每个句式至少有一个"句子 → 公式"的测试。文档贪吃蛇的十条命题全部作为测试，其中 R6、R8、R9 的写法按细则 17.2 调整。

## 10 公式记法与语义

细则 10.1　**记法**沿用文档：
- 逻辑联结词 `¬ ∧ ∨ →`；
- 时序算子 `G F X U W`；
- 量词 `∃ ∃! ∀`，带类型时写作 `∃x:T`；
- `′`（下一状态的值）；
- `₀…₉` 下标（第 k 个状态的值）；
- 比较 `= ≠ < > ≤ ≥`，算术 `+ − × ÷`；
- 谓词和项用函数写法，代码名用反引号。

解析时也接受 ASCII 写法：`! & | -> <= >= != - * /`、`_k` 下标、`'`。

优先级从高到低：`¬`、一元时序算子、`∧`、`∨`、`U`/`W`（右结合）、`→`（右结合）。量词的作用范围延伸到最右。`′` 和下标只能加在项和原子上。

细则 10.2　**语法树。** 公式存为 JSON 语法树，每个节点是 `{"op": …, "args": [...]}`：

| 类 | op |
| --- | --- |
| 联结词 | `not`、`and`、`or`、`implies` |
| 时序 | `G`、`F`、`X`、`U`、`W` |
| 量词 | `exists`、`exists1`、`forall`，带 `var` 和可选的 `type` |
| 比较 | `eq`、`ne`、`lt`、`gt`、`le`、`ge` |
| 算术 | `add`、`sub`、`mul`、`div` |
| 原子与项 | `pred`、`term`，带 `name` |
| 其他 | `var`、`const`（实体名作常量，带 `name`）、`lit`（带 `value`）、`next`（′）、`at`（下标，带 `k`）、`call`、`fails`、`struct`（带 `kind`：exists、signature、contains、calls、only、represents） |

`动作` 是一个特殊的项 `{"op": "term", "name": "动作", "args": []}`，取轨迹状态的 `动作` 字段；动作名写作字符串字面量。

打印出的公式再解析一遍，必须得到同一棵树；测试检查这一点。

细则 10.3　**下一步的两种形式。**
- 公式中的 `X` 按弱下一步解释：轨迹在当前状态结束时，`X φ` 推定为真。这是文档"只要求坏事不发生的命题，没发现违反时得到推定为真"的要求（细则 17.3）。
- 含 `′` 的比较式 `L′ op R` 定义为 `X (L op c)`，其中 c 是 R 在当前状态的值。
- 求值前先做这一改写，再转成否定范式（NNF）。否定经过弱下一步时，变成它的对偶强下一步（¬X̄φ ≡ X(¬φ)，强下一步在轨迹结束时推定为假）；否定经过 G、F、U、W 时，按对偶规则变成 F、G、R、M。
- 强下一步、R、M 只出现在内部的否定范式中，不出现在打印的公式里。

细则 10.4　**命题的类**按语法树判断，不看名称：

| 类 | 判断方式 |
| --- | --- |
| 结构命题 | 含 `struct` 节点 |
| 时序命题 | 含 `G F X U W` 或 `next` 节点 |
| 具体事实 | 其余 |

## 11 对齐 agent 与检查清单（第 6 行）

文档对对齐 agent 的输出"不作规定"。本节只规定 checker 读取检查的接口，不限制对齐 agent 怎样绑定、选什么形态。

细则 11.1　对齐 agent 的输入（文档：命题集、主任务的代码、环境中的工具）：
- 声明；
- 通过检查的命题（编号、来源、句子、公式）；
- W 的路径；
- `align/` 的路径；
- 本节的格式说明。

它的输入里没有需求 R，也没有翻译命题引用的原话（细则 17.4）。

细则 11.2　对齐 agent 写出 `align/checks.json`：

```json
{
  "bindings": {"长度(蛇)": "snake.py 中 Snake.body 的长度", "结束(游戏)": "game.py 中 Game.over"},
  "checks": [
    {"proposition": "R9", "form": "结构检查", "kind": "command",
     "command": "python \"$CV_ALIGN/r9_structure.py\"", "timeout": 60},
    {"proposition": "R4", "form": "插桩加模糊测试", "kind": "trace",
     "command": "python \"$CV_ALIGN/run_snake.py\"", "runs": 50, "timeout": 120}
  ]
}
```

| 键 | 含义 |
| --- | --- |
| `bindings` | 每个声明名称绑定到代码中的什么，文字说明，写进报告 |
| `form` | 形态名称，只写进报告 |
| `kind` | `command` 或 `trace`，决定执行方式和结果的取值 |

细则 11.3　**command 检查。**
- 在 W 中以 `sh -c` 执行一次，环境变量为 `CV_ALIGN`（`align/` 的路径）和 `CV_W`。
- 退出码 0 为通过；1 为失败，标准输出的最后 2000 个字符作为反例；其他退出码、无法启动、超时，都是对齐失败。
- 结果只有通过和失败两种。

细则 11.4　**trace 检查。**
- 执行 `runs` 次，第 i 次设置 `CV_RUN=i`（从 0 开始，供命令作随机种子）和 `CV_TRACE`（轨迹文件路径）。
- 命令把轨迹写到 `CV_TRACE`（第 12 节），由 checker 在轨迹上判定公式（第 13 节）。
- 时序命题得四值之一，具体事实得通过或失败。结构命题不能用 trace 检查。

细则 11.5　**每条时序命题至少要有一条 trace 检查**，command 检查只作补充。这样时序命题的结论来自 checker 对程序生成的公式的判定，而不是来自对齐 agent 所写脚本的退出码。缺少 trace 检查，算对齐失败。

细则 11.6　**对齐失败。** 以下情况都算对齐失败，结果记为失败（对齐）：
- 一条命题没有任何检查；
- 检查格式不合法；
- 时序命题缺少 trace 检查；
- 轨迹缺少公式要用的值；
- "从 S 出发"型命题没有一条轨迹满足其前件（细则 12.5）。

细则 11.7　**格式修正。** `checks.json` 不能解析或格式不合法时，把错误送回对齐 agent 修正一次。仍不合法时，所有命题按对齐失败处理。修正只涉及格式，不告诉对齐 agent 任何检查结果。

细则 11.8　**资源上限**写在 `config.json` 中：

| 设置 | 默认值 |
| --- | --- |
| 每条检查的超时 | 120 秒，`timeout` 不得超过 |
| `runs` 的上限 | 200 |
| 每条轨迹的状态数上限 | 10000，超出截断并注明 |
| 整次 `run_checks` 的预算 | 3600 秒 |

预算用尽后，尚未运行的检查记为失败（对齐），原因写"预算用尽，未运行"。

细则 11.9　checker 自己执行命令，不采信对齐 agent 报告的任何结果。执行的是冻结时的 `checks.json`（细则 5.2）。

## 12 轨迹格式与时间约定

细则 12.1　一条轨迹是 JSON Lines 文件，每行一个状态：

```json
{"实体": {"蛇": ["蛇"], "食物": ["f1"]},
 "值": {"长度(蛇)": 3, "头(蛇)": [4, 2], "尾(蛇)": [2, 2], "格子总数": 100,
        "吃到(蛇,食物)": false, "撞到自身(蛇)": false, "结束(游戏)": false,
        "新生成(食物)": false, "位于蛇身(f1)": false, "移动(蛇)": true},
 "动作": "右"}
```

细则 12.2　**时间约定。** 第 i 个状态记录：
- 时刻 i 的值：位置、数量，以及描述状态的谓词；
- 从时刻 i 到 i+1 这一步中发生的事件谓词（文档声明中"这一步……"的谓词），以及这一步执行的 `动作`。

第 0 个状态是开始时刻，由对齐 agent 决定从哪里开始（例如游戏开局之后）。最后一个状态没有后续的一步，它的事件谓词由对齐 agent 按"这一步没有发生"填写。

按这个约定：
- R4"吃到食物，下一步长度加一"：吃到(蛇, 食物) 在状态 i 为真，表示从 i 到 i+1 这一步吃到了，因此要求长度在 i+1 等于 i 时的长度加一；
- "从 S 出发，依次执行 a1…an，之后 Q"：S 在状态 0 成立，动作₀…动作ₙ₋₁ 依次为 a1…an，Q 在状态 n 成立。

细则 12.3　**值的写法。**
- 键是去掉空白的函数写法，参数是实体名（细则 12.4）或个体编号。
- 谓词的值是布尔值，数量的值是数，位置的值是任意 JSON 值，按 JSON 相等比较。
- 每个状态都要给出公式用到的全部键，缺失算对齐失败。
- 参数中的个体不在本状态的 `实体` 中时，这个原子为假，含它的比较式也为假。

细则 12.4　**实体名作常量。** 实体名作参数时，指该实体在本状态中唯一的个体。轨迹给出 `实体` 时，该实体在每个状态中都必须恰有一个个体，否则算对齐失败。量词在求值的那个状态上取 `实体` 中列出的个体。

细则 12.5　**"从 S 出发"型命题。** 只在动作序列与句子完全相符的轨迹上判定。没有一条轨迹相符时，算对齐失败；否则在相符的轨迹上判定，结果取最差。

细则 12.6　**截断与异常。**
- 命令超时、异常退出时，已写出的轨迹仍按有限前缀判定。
- 退出码非 0 时，这次运行的结果是失败（检查），报告写出退出码和标准错误的末尾。程序崩溃或检查脚本出错，都算作交叉验证没有通过（文档：对齐 agent 出错同样算作交叉验证失败）。
- 轨迹为空时，算对齐失败。

## 13 判定（第 7 行）

细则 13.1　时序命题在一条轨迹上的结果取四值之一，定义来自 RV-LTL（Bauer、Leucker、Schallhart 2010，文档 [28]）：

| 结果 | 含义 |
| --- | --- |
| 确定违反 | 前缀之后无论怎样继续，命题都不成立 |
| 推定为假 | 还不确定；按有限轨迹语义，前缀本身不满足命题 |
| 推定为真 | 还不确定；按有限轨迹语义，前缀本身满足命题 |
| 确定成立 | 前缀之后无论怎样继续，命题都成立 |

细则 13.2　**算法。**
1. 按细则 10.3 改写 `′`，并转成否定范式。
2. 量词在求值的状态上展开为所列个体的合取或析取。
3. 用公式推进（progression）逐个状态改写公式，并用等价规则化简。
4. 结果为 ⊥ 时是确定违反，为 ⊤ 时是确定成立，并记下是在哪一个状态确定的。
5. 否则用有限轨迹语义在最后一个状态上求值：弱下一步、G、W、R 取真；强下一步、F、U、M 取假。真为推定为真，假为推定为假。
6. 非时序命题在第 0 个状态求值，结果为通过或失败。

化简只用等价规则，所以报告为"确定"的结果一定是确定的；但一个实际已经确定的结果，可能只被报告为推定（第 18 节）。

细则 13.3　**结果的顺序**（用于取最差），从差到好：

> 失败（检查）＝ 确定违反 ＜ 失败（对齐）＜ 推定为假 ＜ 推定为真 ＜ 确定成立 ＜ 通过

- 发现缺陷的结果（失败（检查）、确定违反）排在"检查不了"（失败（对齐））之前，免得一个真实的反例被对齐失败盖掉。
- 一条命题在多次运行、多条检查上的结果取最差（文档：多次运行取最差）。报告同时列出每条检查各自的结果。

细则 13.4　**反例。**
- 轨迹检查：写出运行序号、确定或推定的那个状态的序号、到该状态为止的最后 5 个状态；有动作时，写出完整的动作序列。
- command 检查：写出标准输出的末尾。

细则 13.5　**可监控性。** 否定范式中含 F、U 的时序命题（活性成分），在有限运行上通常得不到确定违反。报告中给这类命题加标记，说明它们的推定为假只是没有观察到，不是发现了违反。

细则 13.6　`results.json` 中每条检查一项，包括：命题编号、`kind`、命令、每次运行的退出码、耗时、轨迹文件及其摘要、结果、反例。

## 14 可信度报告（第 8 行）

细则 14.1　`report.md` 沿用文档"检查与判定"一节示例的格式，从上到下依次为：
1. **需求**：R 的每一条整理后的句子，后附原话片段和来源消息编号。积累模式下另列被判为非需求、已被更正、已撤销的消息。还要列出 R 中同时出现在 W 代码里的 ASCII 名字，标为"疑似来自实现"（细则 15.3）。
2. **代码**：项目的提交号；有未提交改动时注明"含未提交改动"，并给出改动的摘要；不是 git 仓库时，给出文件摘要。积累模式下注明快照时间和触发方式。
3. **命题**：每条一行，写出编号、来源、结果、形态、反例。结果相同、编号相邻的可以合并，例如 `R1 至 R3`。活性命题加标记（细则 13.5）。
4. **未通过检查**：被丢弃的命题及原因（细则 9.3）。
5. **绑定**：来自 `checks.json`。
6. **统计**：
   - 提交给检查的命题中，翻译、推理、未套用句式的数量（文档要求）；
   - 其中被丢弃的数量；
   - 各种结果的数量。
7. **比对结论**：见细则 14.2。
8. **说明**：报告是概率凭证；只有满足文档式 (7) 时，通过检查的代码精确率才高于基准正确率。报告不判断式 (7) 是否成立。

`report.json` 包含同样的内容。

细则 14.2　**比对结论**对应文档第 2 章的事件 A，取下列之一：

| 结论 | 条件 |
| --- | --- |
| 无效 | 细则 5.2、5.3、5.4 中任何一条不满足 |
| 无结论 | 没有命题进入检查，或被丢弃的命题超过提交总数的一半（`max_discard_ratio`，默认 0.5） |
| 比对未通过 | 至少一条命题的结果是失败或确定违反 |
| 比对通过 | 其余情况 |

推定为假不计入"未通过"，但在报告中单独列出：文档只说推定为真是安全性质应有的通过结果，没有说推定为假算不通过；而文档建模的前提是"代码正确且子任务都成功时一定通过"，把有限运行上的推定为假计为未通过，会让这个前提不成立。

细则 14.3　工作流的最终输出就是 `report.md` 的内容。积累模式下，启动器把它复制到 `reports/<run>.md`，并更新 `reports/latest.md`。

## 15 需求积累（文档所说的"别的机制"）

细则 15.1　**启用。** 插件只在用户用 `cv init` 启用过的项目中工作。
- `cv init` 拒绝在家目录、根目录启用。
- 不是 git 仓库的项目，要加 `--allow-non-git` 才能启用。
- 未启用的目录里，hooks 立即退出，什么都不做。

细则 15.2　**记录。**
- 阻断型 `user_prompt_submit` hook（很快，`on_error: warn`，保证在 `after_turn` 之前写完）把用户提交的文本追加到当前需求记录。
- iCode 交给这个 hook 的只有用户提交的文本，主 agent 的回复不会进入记录。
- 以下情况不记录：
  - 以 `/` 开头的消息；
  - 载荷中 `session_kind` 为 `workflow`；
  - 环境变量 `CV_INTERNAL=1`（插件自己启动的运行）。
- 记录每行一条：`{"id": "M3", "time": "…", "session": "…", "injected": false, "text": "…"}`。编号在一份记录内递增。追加时持有记录的文件锁。

细则 15.3　**预处理。** 用户可能把代码、报错、主 agent 的回复或交叉验证报告粘贴进对话。这些内容属于主任务的产物，交给子任务就违反约束 3。启动器复制记录时：
- 围栏代码块、形似堆栈的行（`Traceback`、`at …:行号`、`File "…", line`）、绝对路径和含 `/` 的相对路径，替换为 `〔已省略：粘贴的代码或日志〕`；
- 含有报告标记（报告第一行的固定标题 `交叉验证可信度报告`）的消息整条省略，去向固定为非需求；
- 被替换的位置记在 `ledger.jsonl` 中，报告列出受影响的消息编号。

接口名属于需求（文档：需求规定的接口名除外），所以 ASCII 名字不剥离；R 中同时出现在 W 代码里的名字，在报告中列出供用户核对。

细则 15.4　**整理。** `consolidate` 节点由子任务 agent 读预处理后的记录（编号与原文，按时间顺序），输出：

```json
{"requirement": [
   {"text": "下单时总价满 200 元减 30 元。",
    "quotes": [{"from": "M2", "text": "满 100 元减 20 元"}, {"from": "M5", "text": "改成满 200 减 30"}]}],
 "messages": {"M1": "需求", "M2": "已被更正", "M3": "非需求", "M5": "更正 M2", "M6": "撤销 M4", "M4": "已被更正"}}
```

消息的去向：

| 去向 | 含义 | 是否必须被 R 引用 |
| --- | --- | --- |
| `需求` | 给出需求 | 是 |
| `补充` | 追加需求 | 是 |
| `更正 Mk` | 修改先前的 Mk | 是 |
| `撤销 Mk` | 删除先前的 Mk 中的需求 | 否 |
| `已被更正` | 被后来的更正或撤销完全取代 | 否；必须有一条后来的消息以 `更正` 或 `撤销` 指向它 |
| `非需求` | "继续""跑一下测试"、闲聊等 | 否 |

程序检查：
- 每条消息恰好一个去向；
- `Mk` 早于引用它的消息；
- 必须被引用的消息至少被 R 的一条引用；
- R 的每条至少有一个原话片段，片段是所注消息的逐字子串；
- R 整理后的句子中形如 ASCII 标识符的词，都出现在它的原话片段中。

不合格时送回重写一次；仍不合格时，这次运行停止，报告写"需求整理不合格"及原因。

`requirement.txt` 是各条整理后的句子按顺序连接而成的文本。翻译的依据引用原话片段，不引用整理后的句子（细则 6.3）。

细则 15.5　**每次都从原话整理。** 每次运行都从完整的记录重新整理，不在上一次的 R 上修改，避免文档引言所说的规范漂移。

细则 15.6　**新需求。** `cv new` 开始一份新的需求记录，并把 `ledger/current` 指向它。旧记录保留。

## 16 触发、启动器与快照

细则 16.1　**触发方式。** 三种，都针对当前需求记录：

| 触发 | 条件 | 设置 |
| --- | --- | --- |
| 手动 | `cv check` | — |
| 一轮结束 | `after_turn` 且 `status` 为 `ok`，并且自上次运行以来新记录的消息不少于 N 条 | `auto.enabled`，默认开启；`auto.min_new_messages`，即 N，默认 3 |
| 会话结束 | `session_end`，载荷不是工作流会话，并且自上次运行以来有新消息 | `auto.on_session_end`，默认开启 |

会话结束时的那一次最接近最终需求；之前的运行是中间结果，报告注明触发方式。中途触发属于对文档的偏离，见细则 17.5。

细则 16.2　**启动器**是 `cv` 中的函数，hooks 以分离模式（`fire_and_forget` 加 `detach`）调用它，`cv check` 直接调用它。它依次：
1. 取锁（细则 16.3）；
2. 复制并预处理需求记录（细则 15.3）；
3. 做快照（细则 16.4）；
4. 校验工作流来源（细则 5.1）；
5. 在快照目录中运行 `icode workflow run cross-validate --trust --input "@cv-run:<运行目录>"`，环境变量为 `CV_INTERNAL=1` 和 `CV_RUN_DIR`；
6. 复制报告；
7. 删除快照；
8. 释放锁；
9. 有待办标记就再来一次（细则 16.3）。

细则 16.3　**锁与待办。**
- 每个项目一把锁：启动器对 `lock` 加 `flock`，并在整个运行期间持有。进程退出时锁自动释放，没有进程号复用的问题。
- 拿不到锁时，写 `pending` 文件后退出。`pending` 为空文件，存在即表示有待办。
- 运行结束时，如果有 `pending`，并且记录中有这次运行没有看到的消息，就删掉 `pending` 再运行一次；否则删掉 `pending`。这保证最后一条消息总会被检查。
- "上次运行以来的新消息"按 `runs/` 中最近一次 `run.json` 记录的最后一条消息编号计算。

细则 16.4　**快照。**
- 位置是 `~/.chrys/cross-validate/snapshots/<run>/`。
- **复制范围。**
  - git 项目：复制 `git ls-files --cached --others --exclude-standard` 列出且确实存在的文件，子模块用 `git ls-files --recurse-submodules --cached` 补全。
  - 非 git 项目：复制全部文件。
  - 两种情况都排除 `.git/`、`.chrys/`，以及 `snapshot.exclude` 中的目录。
- **依赖目录。** `snapshot.link` 中列出的目录（例如 `node_modules`、`.venv`）以符号链接接入快照，`snapshot.copy` 中列出的被忽略文件（例如 `.env`）照常复制。两者都在报告中注明。
- **符号链接。** 指向项目内部的相对链接按链接复制；其他链接不复制，在报告中列出。
- **上限。** 文件数默认 20000，字节数默认 500 MB；超过时这次运行停止，报告写明原因。
- **一致性。** 复制前后各计算一次源文件的摘要，不一致时重新复制，最多 3 次；仍不一致时，这次运行停止。
- **代码版本。** 记下提交号和未提交改动的摘要。
- **清理。** 运行结束后删除快照（`keep_snapshots`，默认 0）。运行目录保留最近 20 次（`keep_runs`）。

细则 16.5　**hooks 的过滤。** 所有 `cv-` hooks 在以下情况下立即退出：
- 项目未启用；
- `CV_INTERNAL=1`；
- 载荷 `session_kind` 为 `workflow`。

这样插件自己启动的工作流结束时，不会再次触发。用户自己运行的其他工作流，也不会触发交叉验证。

细则 16.6　**报告不交给主 agent。** 报告只写在状态目录中，`cv status` 显示最新结论和报告路径。插件不向主 agent 注入任何内容。主 agent 带 shell，技术上能读到状态目录；插件不在项目中留下任何指向它的路径，并在第 18 节说明。

细则 16.7　**安装与卸载。**
- `cv install` 安装以下几样：
  - 把工作流复制到 `~/.chrys/workflows/cross-validate/`，并记录文件夹摘要；
  - 把两个 agent 配置复制到 `~/.chrys/agents/`；
  - 在 `~/.chrys/hooks/hooks.yaml` 中追加 `cv-` 条目，不改动已有条目。
- 安装后运行 `icode hook validate` 和 `icode workflow validate cross-validate`。
- iCode 首次加载 agent 配置时会改写文件、补上 id，所以安装和卸载按配置的 `name` 识别，不按字节比对。
- `cv uninstall` 只删除插件自己的条目和文件。

## 17 与文档的偏离和对文档示例的调整

细则 17.1　**切句兜底。** 文档规定由子任务 agent 切句，本插件也是。只有它两次都切不对时，才由程序按标点切句；这时所有句子标为 `无`，本次没有翻译命题，报告注明。理由：不让整次交叉验证因为一次切句错误而无法进行。

细则 17.2　**示例句子的写法。** 文档的 R6、R9 按本文法要改写，公式不变：

| 命题 | 文档写法 | 本文法写法 |
| --- | --- | --- |
| R6 | 食物 不 位于 蛇身 上 | 食物 不 位于蛇身 |
| R9 | 代码中存在表示蛇的长度的元素 | 代码中存在表示 蛇的长度 的元素 |

R8 的"游戏 没有结束"在词法阶段自动拆开（细则 8.3），不需要改写。R6 的写法无法与声明 `位于蛇身(食物)` 机械对应。

细则 17.3　**下一步取弱语义。** RV-LTL 原文的有限轨迹语义把 X 作为强下一步。本插件按文档正文"只要求坏事不发生的命题，没发现违反时得到推定为真"，把公式中的 X 作为弱下一步，它的否定才是强下一步（细则 10.3）。否则，轨迹恰好停在"吃到食物"那一步时，R4 这类安全性质会得到推定为假。

细则 17.4　**示例报告中的"通过"。** 文档示例报告把时序命题 R2 至 R4 写作"通过"，而正文规定时序命题取四值之一。本插件以正文为准：时序命题必须有 trace 检查，结果取四值之一（细则 11.5）。同样的代码，本插件报告 R2 至 R4 的结果通常是推定为真。

细则 17.5　**中途触发。** 文档把交叉验证定位为一次性的收尾检查。按用户的要求，本插件在需求积累到一定程度时也会触发（细则 16.1）。为了不破坏文档建模中"主任务与子任务各生成一次、比对一次"的独立性，中途的报告和命题不交给主 agent，也不放在项目里（细则 3.1、16.6）。

细则 17.6　**R 是整理过的需求。** 文档协议的输入是"最终需求原文"。积累模式下，原文分散在多条消息中，并且相互更正。本插件把整理后的句子交给切句，同时保留逐字的原话片段，翻译只引用原话（细则 6.3、15.4），使"翻译照字面、引用原句"仍然成立。

细则 17.7　**`动作`、`接口` 两类声明。** 文档的声明示例中没有这两类，而句式"从 S 出发，依次执行……"、`调用 f(a)` 和结构句式需要它们（细则 7.1）。

细则 17.8　**推定为假不计入未通过，被丢弃过多时为无结论。** 文档没有规定这两点，理由见细则 14.2。

## 18 局限

文档已经指出的：
- 交叉验证不能确保子任务产物与需求的语义一致，只让通过检查的代码与需求对齐的概率更高。
- 同一个模型读偏同一段需求时，查不出这类错误。办法是给子任务配置另一个模型（细则 2.2）。
- 对齐 agent 绑定错误、翻译错误，都算作交叉验证失败。

本实现另有的：
- **需求整理由模型完成。** 整理错了，主任务和子任务会一起错。报告列出原话片段和来源消息，供用户核对。
- **自动触发是启发式的。** 它不知道需求是否已经稳定，只有会话结束时的那次最接近最终需求。`session_end` 在会话回滚到开头、被删除时也会触发，这时会多运行一次。
- **记录的消息可能被撤回。** hook 记下消息之后，用户仍可能撤回这次输入；记录里会留下一条主 agent 没有看到的消息。
- **预处理只认得出常见形式。** 它识别不了的代码或日志仍会进入记录（细则 15.3）。
- **没有沙箱。** 插件能检测改动（细则 5.2、5.4），不能阻止。主 agent 和对齐 agent 都带 shell，以用户的权限运行，技术上可以读写状态目录。
- **iCode 会把工作目录告诉每个 agent。** iCode 在每个 agent 的上下文中附上工作目录的路径。目标模式下，子任务 agent 因此能看到项目的路径（看不到内容）；积累模式下它看到的是快照目录的路径。
- **快照挡不住绝对路径。** 代码中的绝对路径可能让检查读写原项目，快照对此无能为力。
- **有些要求程序检查不了。** "一条命题只说一件事"、"不推测代码如何实现"只在提示中要求。实现上的名字只能识别 ASCII 标识符，中文写的实现名词识别不了。
- **"确定"可能被低估。** 四值判定中，"确定"只依据化简得出，一个实际已经确定的结果可能被报告为推定。活性命题在有限运行上通常只能得到推定（细则 13.5）。
- **检查本身可能写错。** 检查命令由对齐 agent 编写。checker 保证执行的是冻结的检查、结果不来自转述，不保证检查本身写对了，这正是文档模型中的 β。
- **没有空实现对照。** 文档的约束 1（子任务产物要能发现实际会犯的错误）需要在空实现或桩上运行检查才能经验地估计，本插件不做这一步。

## 附：安装与使用

本节不是细则，只说明怎样用。

```
./cv install                 # 安装工作流、两个 agent 配置和 cv- hooks，并运行 iCode 的校验
cd <项目> && cv init         # 在项目中启用需求积累与自动触发
cv check                     # 立即运行一次交叉验证
cv status                    # 最新结论和报告路径
cv new                       # 开始一份新的需求记录
